# 给产品经理从这里开始

如果你拿到的是团队测试反馈、试跑复盘或测试报告，不需要重新按普通项目启动，也不要先去补主路径。

直接对 Codex 说：

```text
这是一次团队产品测试/工作流试跑反馈，不是单纯修某个HTML。
请先复盘这次反馈暴露的工作流问题，并同步到通用工作流文件。
```

如果你不知道怎么开始，不需要先写 PRD，也不需要先整理完整字段、权限和页面清单。

你只需要把下面这句话发给 Codex：

```text
我现在要做一个项目，我该怎么开始？
```

Codex 会先用详细引导方式带你做判断。

第一步不是直接问字段、页面或权限，而是按三轮漏斗推进：

1. 第一轮只确认端口/业务域：工厂端、供应链、市场端、跨域协同，还是不确定。
2. 第二轮再问你手上有没有知识库、现有系统资料、历史资料、规范文档或设计规范来源。
3. 第三轮才判断需求类型、承载系统、是否继承现有系统风格，以及设计规范采用哪种来源。

## Codex 会怎么带你

Codex 不应该一上来让你填完整问卷，而是会先告诉你：

- 现在为什么要问这个问题。
- 这个问题会影响后续什么。
- 常见选项有哪些。
- 推荐选哪个，以及推荐理由。
- 如果你不清楚，可以先标记为待确认。

你可以直接选 A/B/C，也可以说“我觉得 A+B 更接近”，或者说“这个我不清楚，需要业务确认”。

## 你可以准备什么

有就给，没有也可以先不提供：

| 资料 | 有什么用 |
|---|---|
| 一句话需求 | 帮 Codex 判断项目方向 |
| 端口/业务域 | 判断按工厂端、供应链、市场端还是跨域协同规则引导 |
| 知识库或历史资料目录 | 让 Codex 先读已有资料，减少重复追问 |
| 现有系统链接或截图 | 帮 Codex 判断页面风格、菜单、组件和交互 |
| 设计规范来源 | 可以选择工作流已集成规范、现有系统链接反推、产品提供规范文档，也可以先标记暂无 |
| 旧 PRD、流程图、会议纪要 | 帮 Codex 少问重复问题 |
| 表格、字段、单据截图 | 帮 Codex 梳理字段和页面 |
| 角色或权限说明 | 帮 Codex 判断谁能看、谁能操作 |

如果你的需求是放在数智工厂现有系统里，Codex 后续必须读取当前工作流包内的`13_数智工厂系统风格基线/`，不能从零设计一套新风格。该基线已经随包提供，你不需要另外寻找路径。

如果你的需求是放在供应链、市场端或其他已有系统里，Codex 必须先读取对应系统资料，不能默认套数智工厂风格。

设计规范有四种常见来源：

- 已集成规范：工作流里已经沉淀好的系统基线，Codex 会直接读取并说明引用了哪些规则。
- 现有系统链接反推：你提供系统链接、截图或录屏，Codex 先总结页面、组件、交互和视觉规律，再给你确认后作为本项目基线。
- 产品提供规范文档：你提供 Figma、Axure、蓝湖、组件库、UI 规范或交互规范，Codex 会先提炼成项目基线并列出冲突点。
- 暂无规范来源：Codex 只能先整理业务结构稿或页面结构草稿，不能直接生成最终风格 HTML。

## 你不需要做什么

- 不需要先学习所有模板。
- 不需要一开始就会拆角色、流程、字段、状态、权限。
- 不需要替研发回答数据库、接口、技术架构问题。
- 不需要提供旧 HTML 才能生成新原型。

## 你需要确认什么

Codex 会逐步让你确认：

- 这是哪个端口/业务域的需求。
- 是否有知识库、现有系统资料、历史资料可以先读取。
- 这是现有系统新增模块，还是独立新系统。
- 需求最终承载在哪个系统。
- 是否必须继承某个现有系统的页面、组件、权限和 UI 风格。
- 设计规范是使用已集成规范、现有系统链接/截图反推、产品提供规范文档，还是暂时没有。
- 一期做什么，不做什么。
- 页面层级、入口、返回路径是否正确。
- 哪些操作必须有状态变化、权限控制和二次确认。
- 开发实现HTML里是否要提供开发备注/逻辑说明/字段说明入口，方便研发在页面内查看字段、规则和待确认事项；PRD仍保留为正式依据。

只有这些确认到位，才允许进入 HTML 原型生成。
