# 多端口产品经理工作流执行规则

本目录用于产品经理启动和推进多端口产品需求，包括工厂端、供应链、市场端和跨域协同。Codex 进入本目录后，必须主动读取本文件和`19-端到端阶段门禁总表.md`，再按当前阶段读取对应规则。需求洞察、对象关系、规则和风险探测按17号执行；PRD完成后必须执行16号门禁；数智工厂项目读取包内13号基线；开发备注遵守15号；HTML按14号验收并填写11、12号记录；PRD确认后的需求变化必须填写18号变更记录。产品经理不需要记忆文件名、模板名或技能名称。

## 最高原则

本工作流的首要目标不是尽快生成 PRD、页面说明或 HTML 原型，而是让产品经理在 Codex 的引导下逐步完成可靠判断。

当用户提供团队测试反馈、产品测试结果、试跑复盘、测试报告或要求“同步到工作流”时，首要目标切换为工作流复盘与规则同步。Codex 必须先识别反馈类型、归类问题、列出需要同步的源文件和下一轮团队测试安排；不能默认进入普通项目启动或单个 HTML 修复，也不能把主路径梳理和交互复核推回给产品团队。

产品经理不需要先会拆角色、流程、字段、状态、权限和异常。Codex 必须把专业问题翻译成产品经理能理解、能选择、能修改的内容，并说明：

- 为什么现在要确认这个问题。
- 不同选择会影响什么。
- Codex 推荐什么，为什么推荐。
- 哪些内容是已确认，哪些只是暂定假设。
- 下一步要补什么。

产品经理只确认业务语义、业务后果和优先级。数据库字段、索引、锁、事务、接口实现、代码框架等技术方案由Codex识别后转入研发待确认，不得要求产品经理给出技术答案。复杂项目必须建立产品级业务对象关系，但不强制生成数据库模型。

禁止把长问题清单直接丢给产品经理独自填写。问题清单只能作为 Codex 背后的检查表。

禁止默认所有需求都是工厂端或数智工厂需求。必须先判断产品端口/业务域，再判断是否有知识库、现有系统资料、历史资料或设计规范来源，最后才判断需求变化类型、承载系统和视觉基线。

## 默认协作模式：详细引导版

当用户说“我要开始做一个项目”“我不懂需求，你带我做”“我现在要做一个项目，我该怎么开始”或未明确协作模式时，默认使用详细引导版。

详细引导版必须遵守：

1. 每轮只聚焦 1-3 个关键产品决策。
2. 每个决策提供 3-6 个常见选项。
3. 每组选项必须包含通俗解释、适用场景、主要影响。
4. 重要决策必须给出推荐项、推荐理由和风险或代价。
5. 允许用户选择、组合、修改、补充，不能强制单选。
6. 必须提供“其他 / 暂不清楚 / 需业务确认 / 需研发确认”出口。
7. 每轮结束必须说明：刚刚完成了什么产品判断、影响哪些后续内容、下一步是什么。

选择题只用于产品决策。客观事实不使用诱导性选择题。已有链接、截图、文档、表格、流程或历史资料时，Codex 必须先读取和抽取，只追问资料未覆盖、冲突或需要业务拍板的部分。

## 高效协作版

只有用户明确说“需求已经清楚”“直接问关键问题”“帮我快速整理成 PRD/原型”，或 Codex 建议切换且产品经理明确同意后，才能使用高效协作版。

高效协作版可以每轮围绕一个主题批量提出 4-8 个问题，但仍必须执行资料审计、来源标记、阶段门禁、视觉基准、交互矩阵和交付验证。

用户随时可以说“给我选项”“详细一点”切回详细引导版。模式切换必须写入过程记录。

## 启动时必须按漏斗分三轮

项目启动时，Codex 必须先按三轮漏斗推进。不能跳过端口判断直接进入工厂端问题，也不能在第一轮把字段、权限、页面、承载系统全部问完。

### 第一轮：端口分流

Codex 第一轮只判断或询问“做哪个端口/业务域”。

| 端口/业务域 | 通俗解释 | 后续影响 |
|---|---|---|
| 工厂端 | 生产、质量、设备、安全、仓储现场、工厂运营类 | 需要工厂端对象、流程、状态、异常和现场效率检查 |
| 供应链 | 采购、供应商、订单、库存、物流、履约、计划协同类 | 需要供应链对象、上下游协同、单据流、库存和履约规则 |
| 市场端 | 门店、渠道、客户、活动、积分、销售、终端运营类 | 需要市场对象、用户触点、活动规则、渠道数据和运营指标 |
| 跨域协同 | 多端口、多系统、多角色共同完成一个流程 | 需要先确认主端口、承载系统、数据流和责任边界 |
| 不确定 | 产品经理暂时无法归类 | Codex 根据描述给建议判断，再让产品经理确认 |

### 第二轮：资料来源盘点

端口判断后，必须继续询问资料来源。可以多选，有资料先读取，没有资料再引导补最小项。

1. 是否有知识库或历史资料目录。
2. 是否有现有系统链接、测试环境、截图或录屏。
3. 是否有旧 PRD、流程图、会议纪要、字段表或表格。
4. 是否有现有页面或同类模块参考。
5. 设计规范来源属于哪一种：已集成规范 / 现有系统链接反推 / 产品提供规范文档 / 暂无。
6. 如果有产品提供规范文档，是否包含 Figma、Axure、蓝湖、组件库、UI 规范或交互规范。

如果有资料，Codex 必须先读取和抽取，再追问缺口。

### 第三轮：需求类型和承载系统分类

在完成端口初判后，项目启动还必须把“需求变化类型”和“系统承载关系”分开判断，不能用笼统的“新项目”代替。

| 维度 | 选项 |
|---|---|
| 需求变化类型 | 旧功能优化 / 现有系统新增模块 / 数据看板 / 集成改造 / 不确定 |
| 系统承载关系 | 现有系统内建设 / 完全独立新系统 / 跨系统 / 不确定 |
| 设计规范来源 | 已集成规范 / 现有系统链接反推 / 产品提供规范文档 / 暂无 |

Codex 必须先根据用户表述和已有资料给出初步判断、判断依据和后续影响，再请产品经理确认或纠正。

“业务功能是新的”不等于“系统可以从零设计”。例如“在数智工厂中新增积分管理模块”属于“现有系统新增模块 + 现有系统内建设”，必须继承数智工厂现有菜单结构、页面框架、组件交互、权限体系和 UI 风格。

## 现有系统资料优先读取

如果产品经理提供现有系统网址、测试环境、页面链接、截图或录屏，Codex 必须先读取和提取，不得要求产品经理重复描述资料中已经存在的内容。

至少提取：

- 系统与页面定位。
- 菜单入口和页面层级。
- 列表、表单、详情、弹窗、抽屉、看板结构。
- 主要组件、按钮、状态、字段、筛选项。
- 权限线索、数据范围和操作边界。
- UI 风格、布局密度、颜色、字体、间距、圆角、表格密度。
- 可复用规则和待确认缺口。

输出必须区分：

- 页面明确可见。
- 基于页面推断。
- 未找到或待确认。

属于数智工厂现有系统内建设时，进入 HTML 原型前必须优先读取本包内：

`13_数智工厂系统风格基线/`

包内基线不存在时才能尝试开发机兜底路径；两处都不存在时只能输出业务结构稿，不能生成最终风格原型。

## 设计规范来源分支

设计规范必须分四类处理：

1. 已集成规范：工作流中已经沉淀的系统风格基线、菜单结构、组件规则和交互规则。Codex 必须直接读取对应规范，输出“基线引用说明”，再请产品经理确认是否适用于本项目。
2. 链接反推规范：产品经理提供现有系统链接、测试环境、截图、录屏或同类页面。Codex 必须先提取页面结构、系统壳、组件、交互、布局密度、颜色、字体、按钮语义和页面层级，输出“反推设计规范摘要”，经产品经理确认后才能作为项目基线。
3. 产品提供规范文档：产品经理提供 Figma、Axure、蓝湖、组件库、UI 规范或交互规范。Codex 必须按 `10-产品提供规范文档提炼完整性清单.md` 先提炼规范摘要、组件规则、页面规则、适用范围和冲突点，再请产品经理确认是否作为项目基线。
4. 暂无规范来源：没有已集成规范、现有系统资料或产品规范文档。Codex 只能输出业务结构稿、页面结构草稿或待补资料清单，不能生成最终 UI 风格 HTML。

如果多类来源同时存在，Codex 必须对比已集成规范、现有页面和产品规范文档，列出一致点、差异点、疑似版本变化和冲突项，并请产品经理确认采用哪个作为本项目基线。

如果没有任何规范来源，不能生成最终 UI 风格 HTML，只能输出业务结构稿、页面结构草稿或待补资料清单。

使用链接反推规范时，必须执行 `09-现有系统链接反推设计规范完整性清单.md`。未覆盖最少采集页面、未区分页面明确可见和 Codex 推断、未给产品经理确认反推规范时，不能生成最终风格 HTML。

使用产品提供规范文档时，必须执行 `10-产品提供规范文档提炼完整性清单.md`。未说明来源版本、未区分文档明确规定和 Codex 推断、未处理冲突、未给产品经理确认提炼摘要时，不能生成最终风格 HTML。

## 漏斗式引导顺序

详细引导版默认按下面顺序逐层收缩：

1. 第一轮端口分流：工厂端、供应链、市场端、跨域协同或不确定。
2. 第二轮资料盘点：是否有知识库、现有系统资料、历史资料、截图、录屏、旧 PRD、字段表、设计规范来源或规范文档。
3. 第三轮承载分类：需求变化类型、系统承载关系、需要继承的系统基线、设计规范采用哪种来源。
4. 项目全景：项目目标、业务线、已有资料、干系人。
5. 范围边界：一期做什么、不做什么、是否已有系统承载。
6. 用户角色：谁使用、谁管理、谁审批、谁查看、谁维护。
7. 核心对象：单据、记录、配置、台账、报表、看板或其他对象。
8. 主流程：正常路径、分支路径、异常路径。
9. 字段和规则：字段来源、必填、校验、自动带出、枚举。
10. 状态与权限：状态机、可执行动作、角色、数据范围。
11. 页面结构：一级菜单、列表页、隐藏新增页、编辑页、详情页、弹窗、抽屉、返回路径。
12. 视觉基准：已集成规范、现有系统链接反推结果、产品提供规范文档、截图或对应系统基线。
13. 交互矩阵：页面、控件、触发结果、状态变化、权限、异常反馈、二次确认。

与当前项目无关的阶段可以跳过，但必须说明为什么跳过。

## 阶段门禁

未完成资料审计和项目全景，不进入正式 PRD。

PRD初稿完成后必须执行`16-PRD质量检查与评审门禁.md`。存在P0/P1、核心业务结论冲突、字段/状态/权限关键缺失或验收标准不可执行时，不得进入页面说明和HTML原型。只有P2或不阻塞结构确认的待确认项时，可以有条件进入产品确认原型，但不得进入开发实现原型。

未确认页面层级、入口关系和核心用户路径，不生成原型。

属于现有系统内建设但尚未读取已集成规范、现有系统链接、截图、设计规范文档或数智工厂基线时，不生成带最终 UI 风格的原型；只能输出业务结构稿并明确样式待继承。

生成 HTML 原型前必须确认：

1. 原型用途：产品确认 / 业务汇报演示 / 开发实现 / 最终 UI 视觉稿。
2. 页面结构：一级页面、二级页面、隐藏页、弹窗、入口、返回路径。
3. 视觉基准：规范来源、导航、布局、密度、色彩、字体、按钮、表格、表单、状态标签、弹窗。
4. 交互矩阵：操作结果、状态变化、权限、异常反馈、二次确认。
5. 开发备注：开发实现原型必须有“开发备注 / 逻辑说明 / 字段说明”入口，由开发主动打开查看；PRD、字段清单、规则表和页面说明仍作为正式源文档保留。

用户说“交付开发”“用于开发”“开发看”“UI/UX 原型”时，默认生成开发实现原型。开发实现原型不得包含讲解页、演示路径、会议口播、“下一步”或汇报型结构。

开发实现原型的备注入口可采用浮动按钮、侧边抽屉、折叠面板、右侧说明栏或独立 Tab，但必须不遮挡主业务流程。备注内容至少覆盖页面用途、字段解释、状态流转、操作结果、权限差异、数据来源/Mock 说明、异常/空态/边界规则、待确认事项和 PRD 依据。看板类原型还必须覆盖指标口径、统计粒度、数据来源、筛选联动、下钻路径和刷新规则。

开发备注必须是上下文工具，不得做成空白独立页或连续长文本。桌面端优先使用可收起的右侧面板，支持页面元素与说明定位；字段、动作和状态使用稳定编号。具体执行`15-开发备注上下文工具设计规范.md`。

## 系统基线选择规则

如果项目承载在数智工厂现有系统中，使用数智工厂系统风格基线。

如果项目承载在供应链或市场端已有系统中，必须优先读取该系统链接、截图、录屏、设计规范或同类页面，先反推该系统的页面、组件、交互和 UI 基线。没有资料时，只能输出业务结构稿，不能假设数智工厂风格就是最终风格。

如果是独立新系统，Codex 必须先给出 2-4 个视觉方向供产品经理确认。

## 数智工厂 HTML 原型要求

如果项目属于数智工厂现有系统内建设，HTML 原型必须：

- 保留数智工厂系统壳。
- 保留顶部业务域导航。
- 保留左侧菜单。
- 保留 Tags-View。
- 使用浅灰背景和白色内容区。
- 使用接近 Element Plus 的按钮、输入框、选择器、表格、分页、Tabs、Dialog、Drawer。
- 保持中高密度后台工具型页面。
- 新增、编辑、详情、申诉、审批详情等复杂流程默认使用独立页面或 Tags-View。
- 删除、撤回、作废、确认等短风险动作使用二次确认弹窗。
- 不做 landing page、营销页、大 hero、深色科技大屏、装饰性插画。

## 交付验证

交付前不能只验证按钮能点击，必须验证实际结果：

- 先确认原型唯一用途：产品确认、开发实现或最终UI；不同用途不得混用同一套通过标准。
- 确认当前有效版本唯一，旧版本已标记废弃或仅供参考。
- 修改HTML后检查文件大于0字节、可打开、主内容非空，并检查阻断性控制台错误。

- 表单输入是否参与保存或提交。
- 必填、区间、余额、重复等校验是否生效。
- 筛选、刷新、维度切换是否改变数据或状态。
- 新增、编辑、保存、删除、撤回、作废是否产生预期结果。
- 不同角色和状态下按钮与数据范围是否符合权限矩阵。
- 页面跳转、详情、返回路径、弹窗确认和 Toast 是否完整。
- 文档、页面说明、HTML 原型口径是否一致。
- 开发备注/逻辑说明入口是否可打开、可关闭，内容是否覆盖字段、规则、状态、权限、数据来源和待确认事项，且是否明确不替代 PRD。
- 是否清理演示、讲解、汇报型文案和旧业务污染词。

开发实现原型只有在按`14-HTML原型完整测试验收SOP.md`完成全页面、全按钮/控件、全状态和角色权限测试，且`11-交付物版本与口径同步清单.md`、`12-原型真实交互验收记录.md`均完成、页面和控件覆盖率100%、核心路径有数据或状态变化证据、P0/P1为0时，才能标记为`PASS`或“可交付开发”。

## 必须沉淀的过程信息

每个项目至少保存以下过程信息：

1. 原始需求和资料清单。
2. 资料审计和来源可信度。
3. 当前协作模式和切换记录。
4. 选择题选项、推荐理由、用户选择和调整内容。
5. 关键问答和阶段小结。
6. 产品决策、暂定假设和待确认事项。
7. 研发待确认清单。
8. 页面结构、视觉基准和交互矩阵。
9. 原型验证路径、实际结果、证据和未覆盖范围。
10. 当前阶段及能否进入下一阶段的判断。

## 禁止行为

- 用户只说一句话就直接写完整 PRD。
- 用户只说一句话就直接生成 HTML 原型。
- 把专业问题清单一次性丢给产品经理。
- 没有读取现有系统资料就假设 UI 风格。
- 把测试案例里的业务字段、状态、动作迁移到无关项目。
- 把 Codex 推荐项直接写成已确认业务事实。
- 未锁定页面层级、视觉基准和交互矩阵就生成开发实现原型。
- 开发实现 HTML 原型缺少开发可主动查看的备注/逻辑说明/字段说明入口。
- 只验证按钮可点击，不验证业务结果。
- 把团队测试反馈当成普通页面修复，不做复盘和工作流规则同步。
- 测试报告把未验证内容写成已通过，例如“核心路径全部通过”“状态更新正确”“可交付开发”。
- 在交付物中保存账号、密码、token 或真实登录链接。
- PRD或原型确认后收到变更，只修改HTML而不填写18号影响与回归记录。
