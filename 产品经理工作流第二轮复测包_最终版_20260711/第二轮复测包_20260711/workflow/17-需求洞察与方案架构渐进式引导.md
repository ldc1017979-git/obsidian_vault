# 需求洞察与方案架构渐进式引导

用途：吸收需求洞察、数据推演和边界探测方法，但不把专业问题或技术方案推给产品经理填写。Codex先读资料、先判断、先给选项，每轮只确认1-3个关键业务决策。

## 1. 产品经理需要提供什么

产品经理不需要一次性提供完整材料。Codex按阶段引导其补充或确认：

| 阶段 | 产品经理可提供 | Codex必须先做什么 |
|---|---|---|
| 需求洞察 | 原始需求、当前做法、主要痛点、使用人 | 识别需求是问题还是预设方案，提炼真实任务和价值假设 |
| 范围判断 | 一期目标、明确不做、优先级、时间约束 | 给MVP与理想方案对比，说明取舍和影响 |
| 业务对象 | 单据、记录、配置、人员、物料等业务名词 | 从资料提取对象、关系和生命周期草案，让产品确认 |
| 流程状态 | 当前操作过程、审批/确认、异常做法 | 生成正向、逆向、异常流程与状态动作草案 |
| 字段规则 | 页面截图、字段表、表格、旧PRD | 建立产品级字段清单，标出来源、必填、校验、枚举和联动 |
| 权限 | 谁发起、谁处理、谁查看、谁配置 | 生成角色、数据范围、字段读写和动作权限矩阵 |
| 验收 | 做成后怎样算有效 | 将业务语言改写成可操作、可观察、可验证的验收标准 |

## 2. 不应要求产品经理提供什么

以下问题由Codex识别并转入研发待确认，不能要求产品经理给技术答案：

- 数据库字段类型、表结构、索引和分库分表。
- 乐观锁、分布式锁、事务、消息队列和补偿机制。
- 接口协议、错误码、Token续签和具体安全实现。
- React/Vue、TypeScript类型、组件库和代码架构。
- 性能实现方案、部署、监控和回滚技术细节。

产品经理只需确认业务后果，例如“重复提交不能生成两条单据”“多人同时操作时后提交者应收到冲突提示”。

## 3. 第一阶段：需求洞察

### 3.1 识别问题与方案

当用户直接提出“加按钮、加导出、做看板、增加审批”等方案时，Codex先判断：

- 谁在什么场景遇到什么问题？
- 当前如何处理，成本和风险是什么？
- 不做会造成什么影响？
- 该方案是否是唯一解？

不能用质疑或压迫语气。应给出初步判断和2-4个可选方向，让产品经理确认。

### 3.2 需求定义卡片

必要时生成RDD，至少包括：

| 内容 | 要求 |
|---|---|
| 原始需求 | 保留用户原话 |
| 真实痛点 | 当前事实和影响 |
| 用户/JTBD | 谁要完成什么任务、获得什么结果 |
| 业务价值 | 高/中/低及判断依据 |
| MVP与理想方案 | 范围、取舍和风险 |
| 成功指标 | 当前值、目标值、验证方式；无法量化时说明原因 |
| 上下游影响 | 系统、角色、流程、数据和运营影响 |
| 待确认 | 业务/研发分别列出 |

信息不足时RDD只能标记“暂定”，不能作为已确认PRD输入。

## 4. 第二阶段：产品级方案架构

### 4.1 业务对象模型

必做的是产品级模型，不是数据库设计：

| 业务对象 | 对象职责 | 唯一标识 | 上下游关系 | 生命周期 | 数据来源 | 归属系统 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

复杂主子对象、多对多、树形结构和跨系统对象，应画关系图或结构表。数据库表、索引、软删除和锁只写入研发建议，不写成产品已确认事实。

### 4.2 业务规则编号

所有跨页面、跨状态或影响数据结果的业务规则必须编号：

| 规则编号 | 规则名称 | 适用对象/场景 | 条件 | 结果 | 异常 | 确认状态 |
|---|---|---|---|---|---|---|
| R01 |  |  |  |  |  | 已确认/暂定/待确认 |

编号必须在PRD、开发备注和验收用例中复用，规则修改时记录原因和影响范围。

### 4.3 数据与状态推演

对新增、提交、审批、撤回、驳回、确认、作废、同步等关键动作，至少推演：

| 步骤 | 操作前状态/关键数据 | 角色与动作 | 操作后状态/关键数据 | 当前页反馈 | 列表/台账/关联影响 |
|---|---|---|---|---|---|
| 1 |  |  |  |  |  |

推演目的是验证产品逻辑闭环，不要求产品经理提供JSON、数据库字段或接口参数。

## 5. 第三阶段：边界与风险探测

Codex在形成主流程后主动扫描：

| 维度 | 产品经理确认的业务后果 | 转研发确认的技术问题 |
|---|---|---|
| 重复操作 | 是否允许重复、重复后如何提示 | 幂等实现方式 |
| 多人同时操作 | 谁优先、冲突时业务结果 | 锁、版本控制、事务 |
| 部分成功 | 哪些结果保留、是否允许重试/补偿 | 一致性与补偿机制 |
| 权限安全 | 谁能看什么、能做什么、越权反馈 | RBAC、接口鉴权、审计实现 |
| 时间 | 过期、跨日、时区、截止时间规则 | 时间存储和调度方案 |
| 精度/数量 | 金额、数量、比例的业务精度 | 数据类型和计算实现 |
| 大数据量 | 分页、导出、等待和异步体验 | 性能、任务和存储方案 |

风险按P0/P1/P2记录，每条包含场景、业务影响、建议业务规则、待确认角色。

## 6. 第四阶段：规格生成与验证回溯

阶段顺序：

1. 需求洞察：真实痛点、用户任务、价值、范围。
2. 方案架构：对象、字段、规则、流程、状态、权限、异常。
3. 规格生成：PRD、页面说明和验收标准。
4. 质量验证：PRD质量门禁、原型完整验收。

发现问题时必须回到来源阶段：

| 问题 | 回溯阶段 |
|---|---|
| 做错问题、用户或价值 | 需求洞察 |
| 对象关系、字段、流程或状态错误 | 方案架构 |
| PRD章节、规则表达、验收标准问题 | 规格生成 |
| HTML交互、数据绑定或视觉问题 | 原型生成 |

修正后重新执行受影响阶段及后续质量门禁，不允许只修改最终HTML掩盖上游问题。

PRD初稿只能作为草稿。完成16号PRD质量门禁和必要人工评审后，才能标记为当前正式版本；正式版必须保留版本、修订记录、独立AC清单和规则追溯关系。

## 7. 渐进式提问规则

- 每轮只确认1-3个关键业务决策。
- 有资料先读取，不追问资料中已有事实。
- 先给Codex初步判断、选项、推荐理由和影响，再让产品经理确认。
- 客观事实不用诱导式选择题。
- 允许回答“不清楚/待业务确认/待研发确认”。
- 每轮结束说明：刚确认了什么、影响什么、下一步是什么。

禁止把本文件中的表格一次性丢给产品经理填写。
