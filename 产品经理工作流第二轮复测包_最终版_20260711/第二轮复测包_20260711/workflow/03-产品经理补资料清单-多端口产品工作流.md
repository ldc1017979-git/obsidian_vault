# 产品经理补资料清单：多端口产品工作流

这份清单不是启动问卷。

产品经理不需要一开始填完。Codex 应该先用详细引导版帮助产品经理逐步选择、确认和补充。只有资料不足、影响进入下一阶段时，才按本清单补资料。

## 1. 最低启动资料

启动时可以只有一句话需求。

| 资料 | 示例 | 为什么需要 |
|---|---|---|
| 一句话需求 | 想做积分管理、供应商协同、渠道活动管理 | 帮 Codex 判断方向 |
| 端口/业务域 | 工厂端 / 供应链 / 市场端 / 跨域协同 / 不确定 | 决定后续引导问题和专项检查方向 |
| 期望解决的问题 | 线下积分统计混乱、核销不透明 | 帮 Codex 判断目标 |
| 知识库或历史资料 | Obsidian、项目文件夹、历史 PRD、会议纪要 | 决定是否先读资料再提问 |
| 设计规范来源 | 已集成规范 / 现有系统链接反推 / 产品提供规范文档 / 暂无 | 决定原型风格从哪里来 |
| 承载系统 | 数智工厂 / 供应链系统 / 市场系统 / 其他系统 / 独立系统 / 不确定 | 决定是否继承现有系统 UI |
| 当前已有资料 | 链接、截图、表格、流程图、旧 PRD | 决定先读资料还是先引导 |

## 2. 进入 PRD 前需要补齐

以下内容由Codex基于资料先提炼，再按`17-需求洞察与方案架构渐进式引导.md`逐轮请产品经理确认。不得把整张清单一次性交给产品经理填写；数据库、索引、并发锁、接口实现和代码框架转研发确认。

| 类型 | 需要确认什么 | Codex 应如何引导 |
|---|---|---|
| 端口/业务域 | 工厂端 / 供应链 / 市场端 / 跨域协同 / 不确定 | 第一轮先给选项和解释 |
| 资料来源 | 知识库 / 系统链接 / 截图录屏 / 旧 PRD / 字段表 / 产品规范文档 / 已集成规范 / 暂无 | 有资料先读取，无资料再引导补 |
| 设计规范来源 | 已集成规范 / 现有系统链接反推 / 产品提供规范文档 / 暂无 | 第二轮询问，第三轮确认采用哪种 |
| 需求变化类型 | 旧功能优化 / 现有系统新增模块 / 数据看板 / 集成改造 | 给选项、解释、推荐 |
| 系统承载关系 | 现有系统内建设 / 独立新系统 / 跨系统 | 说明是否影响 UI 和菜单 |
| 业务目标 | 为什么做，做到什么算成功 | 给提效、规范、透明、闭环、预警等选项 |
| 一期范围 | 这次先做哪些能力 | 给最小闭环、配置、统计、完整体系等选项 |
| 不做范围 | 哪些能力先不做 | 帮产品经理识别范围膨胀 |
| 用户角色 | 谁新增、谁审批、谁查看、谁维护 | 给常见角色选项 |
| 核心对象 | 单据、记录、配置、台账、报表、看板 | 给对象类型选项 |
| 主流程 | 从哪里开始，到哪里结束 | 用流程选项和示例帮助补齐 |
| 字段单据 | 筛选、列表、表单、详情、明细字段 | 先读表格/截图，再补缺口 |
| 状态规则 | 草稿、待审批、驳回、确认、作废等 | 给常见状态机模板，但必须确认 |
| 权限范围 | 菜单、按钮、数据、字段权限 | 区分产品决策和研发实现 |
| 异常场景 | 填错、重复、无权限、审批失败、数据不足 | 至少补 3 个关键异常 |
| 验收标准 | 怎么判断做完、测过、能交付 | 转成可测试条目 |

## 3. 数智工厂现有系统内建设必须补齐

如果项目放在数智工厂现有系统中，必须确认：

| 类型 | 内容 |
|---|---|
| 菜单位置 | 一级业务域、二级业务子域、业务组、页面 |
| 可见页面 | 哪些出现在左侧菜单 |
| 隐藏页面 | 新增、编辑、详情、申诉、工具页 |
| 页面打开方式 | 独立页 / Tags-View / 弹窗 / 抽屉 |
| 视觉继承 | 是否完全继承数智工厂基线 |
| 组件继承 | 表格、筛选、表单、详情、Tabs、Dialog、Drawer |
| 权限继承 | 角色、菜单、按钮、数据范围 |

Codex 必须读取：

优先读取包内：`13_数智工厂系统风格基线/`

仅当包内目录不存在时，才尝试开发机兜底路径：`/Users/yhl/Documents/Codex项目/产品流程/数智工厂系统风格基线`

如果同时提供了当前数智工厂系统链接或截图，Codex 必须对比已集成基线和当前页面，列出一致点、差异点和疑似版本变化，再让产品经理确认采用哪一个。

## 3.1 供应链或市场端现有系统必须补齐

如果项目放在供应链或市场端已有系统中，必须先提供或引导补充：

| 类型 | 内容 |
|---|---|
| 现有系统资料 | 链接、测试环境、典型页面截图、操作录屏 |
| 同类页面 | 列表、详情、表单、配置、报表、看板样例 |
| 菜单位置 | 所属端口、模块、业务组、页面 |
| 组件规范 | 表格、筛选、弹窗、抽屉、状态标签、按钮 |
| 权限规则 | 菜单、按钮、数据范围、角色 |
| 历史资料 | 旧 PRD、流程图、字段表、会议纪要 |

Codex 不能默认用数智工厂风格代替供应链或市场端风格。资料不足时，只能先输出业务结构稿或待补资料清单。

## 3.2 设计规范来源分支必须补齐

| 来源类型 | 产品经理需要提供什么 | Codex 必须输出什么 |
|---|---|---|
| 已集成规范 | 告诉 Codex 使用哪个已集成基线，或由 Codex 根据承载系统判断 | 基线引用说明、适用范围、不可套用范围 |
| 现有系统链接反推 | 系统链接、测试环境、截图、录屏、同类页面 | 反推设计规范摘要、一致点、缺口、需产品确认项 |
| 产品提供规范文档 | Figma、Axure、蓝湖、组件库、UI 规范、交互规范 | 规范提炼摘要、组件和页面规则、待确认冲突 |
| 暂无 | 说明暂时没有 | 业务结构稿或页面结构草稿，不能生成最终风格 HTML |

反推设计规范摘要至少包含：

- 系统壳：顶部导航、侧边菜单、页签、面包屑或其他框架。
- 页面层级：菜单页、隐藏新增页、编辑页、详情页、弹窗、抽屉。
- 组件规律：按钮、表格、筛选、表单、详情、状态标签、弹窗。
- 视觉规律：颜色、字体、间距、圆角、背景、内容容器、布局密度。
- 交互规律：新增、编辑、详情、删除、导出、审批、返回、二次确认。
- 待产品确认：哪些是页面明确可见，哪些是 Codex 推断。

## 4. 原型前必须补齐

| 类型 | 必须确认 |
|---|---|
| 原型用途 | 产品确认 / 业务汇报演示 / 开发实现 / 最终 UI |
| 页面结构 | 一级页面、隐藏页、弹窗、抽屉、入口、返回 |
| 视觉基准 | 设计规范来源、对应承载系统的系统壳、组件、布局密度、按钮语义 |
| 交互矩阵 | 控件、触发结果、状态变化、权限、异常、二次确认 |
| QA 路径 | 新增、保存、提交、详情、编辑、确认、删除、导出等 |

## 5. 资料不足时的最小补充

如果资料不足，Codex 应只要求补最小必要项：

1. 现有系统链接、典型截图或产品规范文档。
2. 当前流程步骤。
3. 字段或表格。
4. 角色和权限。
5. 异常场景。

不要一次性要求产品经理补完整 PRD。

## 6. 资料状态判断

| 状态 | 含义 | Codex 动作 |
|---|---|---|
| 已有可直接用 | 资料明确、当前有效 | 直接引用并标来源 |
| 已有但需抽取 | 资料存在但未结构化 | 先抽取，不重复追问 |
| 版本或口径冲突 | 多份资料说法不同 | 列冲突，请产品经理确认 |
| 待确认 | 信息不完整或需要拍板 | 给选项和影响说明 |
| 未找到 | 关键资料没有 | 说明影响和最小补充项 |

## 7. 禁止把清单变成开局作业

Codex 不允许这样做：

```text
请你先完整填写下面 16 类问题，我再开始。
```

正确做法是：

```text
我先根据你的一句话做初步判断。现在只需要你确认 1-3 个关键方向，我会给选项。
```
