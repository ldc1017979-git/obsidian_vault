# HTML原型完整测试验收SOP

用途：对产品确认原型、开发实现原型和最终UI进行完整测试验收，防止只检查首屏、少数按钮或静态页面。开发实现原型必须执行完整流程；产品确认原型允许部分功能未实现，但必须逐项标记`未实现/未覆盖`，不能写PASS。

## 0. 验收原则

1. 先盘点，后测试。没有页面、控件和状态清单，不开始验收。
2. 所有可见按钮、链接、Tab、菜单、筛选、分页、弹窗、抽屉、表单控件都必须逐项测试。
3. “可点击”只代表事件触发，不代表功能通过；必须核对页面、数据、状态、Toast和返回列表结果。
4. 每个结论必须有截图、快照、日志或操作记录证据。
5. 未覆盖项必须明确列出，不能用“核心功能基本通过”代替。

## 3. 第一轮：文件与页面冒烟

- [ ] HTML大于0字节，可打开且主内容非空。
- [ ] 所有菜单和页面入口可到达。
- [ ] 页面标题、面包屑、Tags-View和返回路径正确。
- [ ] 所有静态资源成功加载，无阻断性控制台错误。
- [ ] 弹窗、抽屉和遮罩可以正常打开、关闭。
- [ ] 所有页面均截图留证，不只截首屏。

冒烟失败时停止后续验收，先修复再重新开始。

## 4. 第二轮：全按钮与控件测试

逐页面执行控件清单：

- [ ] 顶部导航、侧边菜单、页签、面包屑。
- [ ] 搜索、重置、展开/收起、刷新、列设置、导出。
- [ ] 新增、保存草稿、提交、取消、返回。
- [ ] 详情、编辑、复制、删除、启停。
- [ ] 审批、驳回、确认、撤回、作废、申诉、核销等业务动作。
- [ ] 分页、每页条数、跳页、排序。
- [ ] Tab、维度切换、图表筛选和下钻。
- [ ] 开发备注/逻辑说明的打开、关闭和滚动。
- [ ] 按`15-开发备注上下文工具设计规范.md`验证页面元素与备注定位、结构化分组、搜索/编号和主页面可操作性。

每个控件必须记录：点击前状态、操作、实际反馈、数据/状态变化和截图。无响应、仅装饰或仅文本模拟的控件必须标记FAIL或“未实现”。

## 5. 第三轮：表单与数据闭环

### 5.1 字段

- [ ] 新增态为空或默认值正确。
- [ ] 编辑态正确回填当前记录。
- [ ] 详情态展示当前行对应数据且只读。
- [ ] 必填、长度、格式、范围、精度、重复、余额和关联校验生效。
- [ ] 下拉枚举、联动、自动带出、计算字段正确。
- [ ] 上传的格式、大小、数量和删除规则有反馈。

### 5.2 保存与提交

- [ ] 保存草稿后数据保留，状态正确。
- [ ] 提交后显示明确结果和下一状态。
- [ ] 返回列表出现新增/更新记录。
- [ ] 再次进入详情或编辑时数据一致。
- [ ] 刷新页面后结果仍符合原型约定；无持久化能力时明确标记。

## 7. 第五轮：角色与权限

至少覆盖管理员、发起人、审批人、普通用户和业务专项角色；不适用角色写N/A。

- [ ] 菜单可见性。
- [ ] 数据范围。
- [ ] 按钮显示、隐藏或禁用。
- [ ] 无权限访问页面/详情的反馈。
- [ ] 同一记录在不同角色下的动作差异。
- [ ] 越权操作不会产生数据或状态变化。

## 8. 第六轮：异常、边界与空态

- [ ] 无数据和无搜索结果。
- [ ] 必填缺失、格式错误、超长、最小/最大值。
- [ ] 重复提交、连续点击、取消操作。
- [ ] 接口/同步失败模拟及失败原因。
- [ ] 无权限、已失效、状态已变化。
- [ ] 列表大数据、宽表、长文本、长文件名。
- [ ] 空附件、图片加载失败、异常枚举。
- [ ] 错误后可恢复，不产生错误状态。

## 9. 第七轮：视觉与响应式

每个目标视口检查全部页面和所有打开状态：

- [ ] 文字无溢出、遮挡、重叠和截断误导。
- [ ] 表格列可查看，固定列和横向滚动正常。
- [ ] 表单标签、输入框、按钮对齐。
- [ ] 弹窗、抽屉、下拉和遮罩不超出视口。
- [ ] Toast不遮挡关键操作。
- [ ] 移动端没有桌面评审壳或说明栏挤压页面本体。

## 10. 第八轮：文档与安全扫描

- [ ] PRD、页面说明、HTML、开发备注字段一致。
- [ ] 开发备注不是空白页或长文本堆叠，关键字段和动作可在30秒内定位。
- [ ] 状态、动作、权限、待确认项一致。
- [ ] 基线来源和当前有效版本描述正确。
- [ ] 无账号、密码、Token、真实登录链接和不必要人员信息。
- [ ] 测试数据为虚构或脱敏数据，不含生产凭据，并明确测试后清理方式。
- [ ] 无旧业务污染词、演示讲解文案和错误测试案例字段。

## 12. 验收判定

### PASS

- 页面清单和控件清单100%完成。
- 核心主流程、状态、数据绑定、返回同步和角色权限均有证据。
- P0/P1为0，P2已明确接受或排期。
- 所有目标视口通过。
- 文档与HTML一致，敏感信息扫描通过。

### REVIEW

- 产品确认原型方向可评审，但存在明确未实现/未覆盖项；或非核心P2待确认。
- REVIEW不能称为“开发可用”或“最终完成”。

### FAIL

- 存在无响应核心按钮、必填无效、状态不更新、详情数据错误、返回列表不同步、权限越权、文件不可用或P0/P1未关闭。
- 页面/控件清单未完成，直接判FAIL，不允许按抽样结果写PASS。

## 14. 业务UAT与发布准备

内部HTML QA达到PASS后，才可进入业务UAT。业务UAT验证业务场景、规则口径和角色结果，不重复冒充技术全量测试。

- [ ] 业务验收人、场景、数据和结论可追溯。
- [ ] 支持浏览器/设备范围已实测；键盘操作、焦点、标签、错误提示、颜色对比等基础无障碍项已检查或说明不适用。
- [ ] P2、未覆盖项和依赖已由明确负责人接受或排期。
- [ ] 真实上线项目已明确发布负责人、监控、灰度和回滚/恢复；纯原型标记不适用。
- [ ] UAT中产生的需求变化按`18-需求变更与影响回归记录.md`回到对应阶段，不能直接改HTML后签收。
