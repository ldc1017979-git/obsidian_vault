## 目标

把活动规则、需求资料、字段汇总和历史模板转成可打印、可手写、可验收、可追责的上线点检表。点检表要帮助后端配置人员和前端业务验证人员少走回头路，而不是只做管理汇总。

## 默认交付

- Markdown 预览版
- Excel 执行版：可见页签只保留 `打印填写版`
- 活动基础口径 sheet（内部隐藏或单独留存）
- 资料覆盖验证 sheet（内部隐藏或单独留存）
- 生成校验 sheet（内部隐藏或单独留存）
- 原始模板保留 sheet（如用户提供）

不默认附带“验证数据准备清单”。点检表只制作点检项目；如用户明确要求，再单独生成验证数据准备清单。

## 来源优先级与范围边界

当资料之间口径冲突时，按这个顺序取值：用户最新确认 > 当前活动规则 > 需求资料 > 周年活动汇总/字段说明 > 历史模板。

点检表默认只覆盖本活动的消费者链路和商户链路。消费者/商户相关配置、页面、扫码、核销、支付、奖励、异常状态要纳入；三级客户、二级客户、经销商、配送商等上游奖励或截止时间，不因为字段汇总里出现就自动纳入本活动点检表，除非当前活动规则明确要求它参与消费者/商户流程，或用户明确要求另做项目点检。

奖励类型是相对固定的，但本次口径必须从活动规则读取。常见奖励族包括：红包、产品券、1元换购券、积分额度/能量额度、高价值奖品。不要凭历史活动套金额、次数、有效期、中奖率或兑换门槛。

## 打印填写版

第一张 sheet 必须是 `打印填写版`。它是给后端配置人员和前端业务验证人员实际打印填写的主表。

推荐列：

| 列 | 名称 | 说明 |
|---|---|---|
| A | 编号 | 稳定编号，例如 A01、B02、K17 |
| B | 模块 | 来源模块或业务模块 |
| C | 码入口 | 全局、拉环内码、拉环外码、箱内码、核销/商户等；时间/有效期类正式点检项不能写全局 |
| D | 检查项 | 单个可判断的事项 |
| E | 检查标准 / 本次口径 | 本活动应确认的具体配置或预期 |
| F | 验证动作 | 短动作，例如后台查看配置、扫码验证、核销一张券 |
| G | 结果 | 空白，手写 √ / × / - |
| H | 备注 | 空白，不通过或不涉及时手写原因 |

如页面空间足够，也可拆成 `检查标准` 和 `本次口径` 两列。

## 编号行职责

打印填写版的编号行只负责一件事：让负责人员按点检项目执行，并在结果列填写 `√ / × / -`。编号行不能承担说明、指导、提醒、覆盖关系说明、验证方法介绍、点检表使用说明。

保留编号行的硬标准：

- 能明确由某个角色执行。
- 能明确知道去哪看、扫什么码、核对哪个页面/字段/流水。
- 能明确判断通过、不通过或不涉及。
- 不能判断时，应改写成具体点检项，或移到风险确认/资料覆盖验证/备注材料，不进入打印填写版。

纯元数据不进入编号点检行。活动名称、项目名称、环境、验证负责人、验证日期、版本/构建号等已经出现在表头或 `活动基础口径` sheet 中，不应再生成 `后台活动名称` 这类编号行；除非活动名称本身会影响系统路由、消费者页面选择或其他线上风险配置。

错误写法：

```text
检查项：配置预览校验
检查标准：发布前系统预览能发现活动时间、区域、码类型、奖池等配置错误
验证动作：后台查看配置
```

这类写法只是说明“预览功能有用”，不是点检项目。除非后台真的有一个明确的预览页，并且写清楚核对字段，否则应删除或拆成具体点检项。

清晰写法：

```text
检查项：箱内码活动预览页字段核对
检查标准：预览页的箱内码活动时间、活动区域、码类型、红包档位与后台配置一致
验证动作：打开后台箱内码活动预览页核对
```

## 支撑 sheet 标准

交付给执行人员的工作簿，打开后可见页签必须克制：

- `打印填写版`：必显，给后端配置人员和前端业务验证人员填写。

以下支撑 sheet 可生成，但默认隐藏或单独留存，不作为执行人员可见页签：

- `活动基础口径`：列出本次活动名称、环境、版本、各码入口时间、区域、产品、码类型、奖励类型、商户范围、支付/核销商户号、扫码上限、页面文案来源等关键口径；未知项写“待确认”，不要空着假装已确认。整体活动时间可作为资料摘要记录在这里，但正式点检明细中的时间项必须绑定具体码入口或权益路径。
- `上线前风险确认`：只放会影响上线判断的冲突、缺失、客户/业务待确认口径；确认结果和备注保持空白，留给线下确认填写。
- `上线点检表`：保留完整明细和主责字段，便于筛选；结果和备注保持空白。
- `资料覆盖验证`：记录每份规则/需求/知识库资料是否已转成点检项、风险确认项或明确判定为不属于系统点检。
- `生成校验`：记录数量、唯一编号、重复编号、未分组编号、后端/前端数量、结果/备注空白校验等。
- `原始模板保留`：仅在用户提供旧模板且需要保留时添加。

不应让执行人员看到一排内部校验页签；页签过多会降低执行率，并让责任人误以为每个 sheet 都要填写。打印填写版是唯一默认可见页，其他 sheet 只用于制表人自检或按需另发。

## 时间与有效期归属

时间一定服务于具体的码入口、权益或核销路径，不作为悬空的全局点检项。正式点检明细里，凡是检查项或标准涉及活动开始、活动结束、扫码时间、有效期、兑换截止、核销截止、过期处理，都必须明确归属到具体 `码入口`。

正确写法示例：

```text
码入口：箱内码
检查项：箱内码活动开始时间
检查标准 / 本次口径：规则写“即日起”，后台必须配置明确开始时间

码入口：箱内码
检查项：箱内码活动结束时间
检查标准 / 本次口径：即日起至2027年12月31日

码入口：拉环外码
检查项：拉环外码促销扫码截止日

码入口：产品券
检查项：产品券有效期

码入口：商户核销
检查项：商户核销截止时间
```

错误写法示例：

```text
码入口：全局
检查项：活动开始时间

码入口：全局
检查项：活动结束时间
```

如果同一个时间同时适用于箱内码和拉环码，优先拆成两条独立点检项；只有当后台确实是同一个配置项且一次查看即可验证时，才允许合并，但 `码入口` 必须写成 `箱内码、拉环码` 这类明确列表，不能写 `全局`。

## 内容清晰度标准

每一条正式点检项必须让执行人不用猜就知道怎么做。单行必须同时回答四个问题：

- 对象/路径：服务于哪个码入口、权益、页面或后台模块，例如箱内码、拉环内码、产品券、商户核销、规则页。
- 检查内容：具体检查哪个字段、页面、状态、流水或异常场景。
- 预期结果：本活动应是什么值、什么文案、什么状态，或明确“不涉及/确认未配置”。
- 验证动作：在哪里看、怎么扫、怎么核销、导出什么数据、找谁确认。

不清晰写法：

```text
检查项：配置预览校验
检查标准：发布前系统预览能发现活动时间、区域、码类型、奖池等配置错误
验证动作：后台查看配置
```

清晰写法：

```text
检查项：箱内码活动预览页配置核对
检查标准：预览页展示箱内码活动时间、活动区域、码类型、红包档位与后台配置一致
验证动作：打开后台活动预览页核对
```

动作要与内容匹配：

- 实物包装、拉环字样、纸箱标识、包装打样：归入前端业务验证，使用 `查看确认记录`，并写明确认依据。
- 页面规则、热线、不可兑换现金、个税、合规说明：用 `页面核对`，不要写成后台功能测试。
- 后台配置项：用 `后台查看配置`，但检查项和标准必须写出具体配置字段。
- 流水/看板/导出：不要只写“后台流水完整”或“数据看板可看”，要按拉环核销、箱内码红包、提现、异常数据等拆成可核对行。

确认记录类行必须写清确认依据，例如活动规则、客户确认记录、业务确认记录、包装打样、页面截图。否则执行人不知道找谁或找哪份资料确认。

## 分组原则

主表不是按资料原顺序，也不是按模块字母顺序。主表按执行路径重排：

1. `大板块：后端配置确认`
2. `大板块：前端业务验证`

每个大板块下面按一次性可验证的配置块或验证场景分组。分组行只做视觉分隔，不能替代明细行。

正确示例：

```text
大板块：后端配置确认
一次性验证分组：箱内码红包活动配置
H01 箱内码活动数量 ...
H02 箱内码红包档位 ...
H03 箱内码中奖率 ...
H04 箱内码活动时间 ...
H05 箱内码扫码有效期 ...
H06 箱内码每日上限 ...
H07 提现规则 ...
H08 箱内码类型 ...
H09 箱内码参与对象 ...
```

错误示例：

```text
B09 箱内码红包活动配置 覆盖 H01、H02、H03...
```

这种汇总行会让执行人来回跳明细，容易遗漏，不作为主点检表结构。

## 后端配置确认常见分组

- 活动主配置与发布状态
- 箱内码 / 拉环码时间与有效期配置
- 区域、名单与商户范围配置
- 产品、码源与活动商品绑定
- 码类型隔离、真实性与追加审批
- 奖池、中奖率与券模板配置
- 商户号、支付与奖励配置
- 箱内码红包活动配置
- 箱内码门店 / 商户归属配置
- 后台规则页、客服合规与风控配置
- 后台流水、看板、预警与导出
- 停用归档、终止保障与授权留痕

后端配置必须特别关注：

- 活动名称、活动类型、规则版本、发布状态
- 按码入口或权益路径分别确认开始时间、结束时间、扫码有效期、券有效期、兑换截止日、核销截止日
- 活动区域、排除区域、商户白名单、历史模板残留
- 产品规格、SAP物料、码源批次、生产日期、活动绑定
- 码类型、码前缀、活动隔离、非本活动码拦截
- 奖池、中奖率、库存扣减、券模板、券类型
- 核销商户号、支付商户号、支付流水归属
- 消费者/商户奖励配置、扫码、中奖、发券、核销、支付、奖励流水
- 数据看板、导出、预警、归档

## 前端业务验证常见分组

- 消费者入口、授权与规则展示
- 拒绝授权 / 拒绝规则确认
- 拉环外码页面展示
- 拉环中奖 / 未中奖领券流程
- 每日扫码上限
- 重复扫码与一码一次
- 超区域扫码与回到活动区
- 券过期、活动结束与停用后保障
- 商户核销、1元支付和支付失败
- 箱内码红包领取、余额和提现
- 箱内码门店 / 商户前端限制
- 异常码、非本活动码和未设置字段
- 活动隔离
- 业务员APP查看
- 看板导出对账验证

前端业务验证必须站在执行人视角：同一个用户路径能验证的点放在一起，但每个检查点仍保留独立行。除后端配置人员确认的系统配置外，页面、扫码、实物标识、确认记录、规则一致性、商户/消费者业务结果都归入前端业务验证。

## 奖励类型场景库

按活动规则选择对应场景，不要机械全加；同一个扫码路径能一次验证的项目应连续排列，但每个检查点仍保留独立行。

| 奖励类型 | 后端配置必看 | 前端业务验证必看 |
|---|---|---|
| 红包 | 红包档位、中奖率、库存/预算、领取/提现规则、发放流水 | 中奖、未中奖、重复扫码、余额/提现、失败提示 |
| 产品券 | 券模板、券类型、有效期、兑换门槛、核销商户/门店范围 | 获券、券包展示、到店核销、过期/已核销状态 |
| 1元换购券 | 券模板、支付商户号、核销商户号、支付金额、兑换截止日 | 领券、1元支付、支付成功/失败、商户核销 |
| 积分额度/能量额度 | 额度来源、累计规则、兑换门槛、扣减规则、有效期 | 扫码累计、达到门槛、兑换发券、扣减后余额 |

如果活动规则只说线下付款或线下交付，不把支付/交付当系统功能验证；但页面展示了付款、兑换、交付说明时，必须做页面文案核对。

## 高价值奖品

高价值奖品属于必检项。出现 888元、金牌、电动车或类似高价值奖品时，至少检查：

- 奖品名称、数量、价值、中奖率或奖池配置
- 中奖后身份信息采集字段，如姓名、手机号、身份证、微信号等
- 领奖截止时间、逾期处理、资格限制
- 税费/代扣代缴、累计奖品价值上限等页面文案或配置
- 奖品发放、签收、客服跟进、后台状态流转
- 未成年人、安全责任、物流/到店领取等规则文案如有展示必须核对

## 集能量 / 再抽奖

集能量、积分额度、再抽奖不并入普通红包或 1元换购点检表。它们是独立活动引擎，可以基于某个消费者促销活动产生资格或来源码，但点检表应单独生成。

独立点检时至少覆盖：

- 来源活动、来源码类型、来源权益是否准确
- 未中奖或指定行为是否累计能量/积分/再抽奖资格
- 累计阈值、兑换门槛、兑换后扣减
- 发券/发红包/再抽奖结果、有效期、重复兑换限制
- 能量/积分余额、流水、异常回滚、页面文案

## 线上 / 线下责任边界

- 线下收拉环、收瓶盖、线下换购：不默认加入消费者线上支付；重点看商户扫码/核销、活动页面文案、凭证和后台配置。
- 线上1元换购：按规则检查消费者扫码、领券、支付、支付商户号、核销商户号、商户核销和支付失败。
- 箱内码：先判断是消费者扫码、商户扫码，还是两者都有；再分别放入对应前端业务验证分组。
- 消费者直扫但规则要求给商户扫码时，要验证消费者侧提示、不能核销、不能消耗权益、不能生成有效奖励流水。
- 商户使用彬纷有礼小程序/APP等指定入口时，前端业务验证应写明入口，不写泛泛的“商户端”。

## 页面文案 / 规则一致性

页面文案核对是默认必做项。即使某些内容不是系统功能，也要检查活动页面、规则页、扫码结果页、弹窗、异常提示页展示的信息是否与活动规则一致。

必须考虑的页面核对内容：

- 活动名称、活动主题、活动时间、活动范围
- 产品范围、规格、口味、实物图样说明
- 奖品/权益说明、红包档位、中奖率、市场价值等展示信息
- 兑换方式、商户扫码说明、消费者扫码说明
- 活动结束、未激活、超范围、重复扫码、已被他人扫码、扫码上限等异常文案
- 客服热线、工作时间、隐私/法律/争议处理等注意事项

处理原则：

- 线下付款、线下交付饮料、实物标识、法律条款等不作为系统功能验证。
- 只要这些内容展示在页面上，就作为 `页面文案核对` 或 `规则一致性核对` 点检。
- 页面文案如果由平台固定模板提供，也仍要核对触发页面是否展示正确文案。
- 如果文案可配置，要核对后台配置值与前端展示值一致。

## 不涉及 / 确认未配置

如果规则没有提到某个能力，但平台模板、历史活动或后台配置中可能存在该字段，且错误残留会影响线上结果，要加入 `不涉及/确认未配置` 点检项。

常见需要反向确认的字段：

- 券有效期、兑换截止日、过期处理
- 积分/能量额度、红包、产品券、1元换购券、奖励券
- 单日上限、单月上限、总次数上限
- 商户白名单、黑名单、区域排除
- 旧活动码类型、旧奖池、旧券模板、旧活动规则页
- 支付商户号、核销商户号、奖励流水配置

写法示例：

```text
检查项：积分奖励配置
检查标准 / 本次口径：本活动不涉及积分奖励，后台确认未配置积分发放规则
验证动作：后台查看配置
```

点检项数量控制原则：系统功能点检保持克制，优先列真正可能导致线上事故的配置和路径；页面文案核对、确认记录、风险确认可以单独列清楚，不要把所有规则说明都塞成系统功能测试。

反向确认也要遵守范围边界：只列可能影响消费者/商户链路的残留配置。三级客户、二级客户、经销商、配送商等上游项目字段不自动加入，除非当前活动规则明确要求。

## 扫码异常 / 限制态场景库

只要活动涉及 `箱内码扫码`，默认必须检查下面这些候选场景。只要活动规则允许消费者参与扫码，也必须按同一套候选场景判断是否纳入点检表。商户扫码、业务员扫码、消费者扫码的责任边界要先判断清楚，再决定放在哪个前端业务验证分组。

这些场景不是机械全加。原则是：规则有对应限制、平台有通用限制、或线上可能出现且会影响码状态/权益发放的，就要变成独立点检项；规则完全不涉及且系统无该能力时，放入“不涉及/确认未配置”或不加入正式系统测试项。

常见候选场景：

| 场景 | 触发条件 | 点检关注点 | 典型预期 |
|---|---|---|---|
| 二维码未激活 | 码批次未激活、活动未开始、码未绑定活动 | 不发权益，不核销，不产生有效领取流水 | 页面提示“二维码未激活”或活动未开始类文案 |
| 超活动范围 | 用户定位、门店、经销商、码批次、活动区域不满足规则 | 不发权益，不核销；是否消耗码按活动规则/平台规则确认 | 页面提示超出活动范围，无法参与活动 |
| 重复扫码 | 同一用户再次扫描已领取/已参与的同一二维码 | 不重复发放红包、券、中奖权益；展示首次扫码/领取信息时要准确 | 页面提示已领取过/已参与过 |
| 已被他人扫码 | 二维码已被其他用户领取或核销后再次被扫 | 不给当前用户发权益；展示已被领取状态和必要时间信息 | 页面提示该二维码已被扫描领取 |
| 单日活动上限 | 同一用户达到活动规则规定的每日扫码次数 | 不继续参与；未扫过二维码是否消耗按规则确认 | 页面提示今日扫码已达上限，并说明次日再扫 |
| 单月活动上限 | 同一用户达到活动规则规定的自然月扫码次数 | 不继续参与；未扫过二维码是否消耗按规则确认 | 页面提示本月扫码已达上限，并说明次月再扫 |
| 活动已结束 | 当前时间晚于活动截止时间，或码超过扫码有效期 | 不发权益，不核销，不产生有效领取；已获得且有效权益是否保障按规则确认 | 页面提示活动已结束或已过期 |

写进点检表时，不要只写“异常场景验证”。要拆成可执行行，例如：

- 箱内码二维码未激活
- 箱内码超活动范围
- 箱内码同用户重复扫码
- 箱内码已被他人扫码
- 箱内码单日扫码上限
- 箱内码单月扫码上限
- 箱内码活动已结束

如果活动规则写了具体次数或文案，必须写入本次口径，例如 `单日10次`、`自然月30次`、`请保留二维码明日再扫`。如果规则没有写具体次数，但截图、需求或平台配置里出现了次数，列为客户/业务确认项，不能默默套用。

## 结果和备注

- 结果列每行空白，由负责人员手写 `√`、`×`、`-`。
- 不要每行重复写 `□通过 / □不通过 / □不涉及`。
- 不要每行预填 `不通过/不涉及原因`。
- 备注列空白。不通过或不涉及时，由填写人写原因。
- 结果说明放在大板块或分组行右侧：`结果填写：√通过 / ×不通过 / -不涉及`。

## 验证动作写法

验证动作要短、可执行，不要写成长说明。

推荐词：

- 后台查看配置
- 页面核对
- 扫码验证
- 重复扫码验证
- 扫码到上限验证
- 定位/区域验证
- 核销一张券
- 1元支付验证
- 查看后台流水
- 提现流程验证
- 导出数据核对
- 查看确认记录

## 编号和覆盖校验

生成后必须校验：

- 正式点检项数量
- 编号是否唯一
- 是否有重复编号
- 是否有未分组编号
- 后端/前端业务验证大板块数量
- 每个来源规则是否至少覆盖到一个点检项或风险确认项
- 打印版结果列和备注列是否为空白

最终回复用户时必须说明这些校验结果。
