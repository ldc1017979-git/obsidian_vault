# 看板类产品经理执行SOP

## 1. 使用场景

当需求属于以下任一类型时，优先使用本SOP：

- BI看板
- 经营驾驶舱
- 数据分析专题
- 运营监控页面
- 预警看板
- 明细下钻和运营跟进清单

看板类项目不要从页面开始，而要从业务问题、数据粒度和指标口径开始。

## 2. 标准流程

```text
一句话需求
-> 业务问题确认
-> 使用人和动作确认
-> 数据源和字段盘点
-> 表粒度判断
-> 指标口径字典
-> 数据验证
-> 中间表/输出数据集
-> 看板结构设计
-> 单文件HTML原型
-> 浏览器验证
-> 开发交付包
```

## 3. 第一步：不要直接做图

产品经理拿到一句需求后，先让Codex输出：

1. 需求类型：监控、诊断、复盘、对比、预警、运营清单。
2. 业务问题：这个看板到底要回答什么。
3. 使用人：管理层、业务负责人、运营、一线主管、数据分析人员。
4. 看完后的动作：决策、调度、跟进、复盘、预警处理。
5. 当前资料是否足够。
6. 必须确认的3-5个问题。

只有这些明确后，才进入字段和页面设计。

如果产品经理只会说“我现在要做数据分析，我应该怎么做”，先使用 `00-一句话启动入口.md`，让Codex自动发起第一轮5个关键问题。

## 4. 第二步：先判断数据粒度

字段表或样本进来后，先判断一行数据代表什么：

| 粒度 | 适合分析 |
|---|---|
| 用户 | 留存、复购、生命周期、分层 |
| 事件 | 行为路径、转化、频次 |
| 订单 | 销售、客单、退款、履约 |
| 门店+日期 | 动销、活跃、缺货、补货 |
| SKU+日期 | 商品趋势、结构、异常 |
| 汇总维度 | 趋势和对比，不能做明细下钻 |

如果粒度不清楚，不能计算指标。

## 5. 第三步：指标必须先写口径

每个指标至少写清：

- 指标名称
- 业务含义
- 统计对象
- 分子
- 分母
- 时间窗口
- 去重规则
- 排除规则
- 维度
- 数据来源
- 页面解释方式

比例类指标必须能从分子、分母反推；分桶类指标必须合计等于总体。

## 6. 第四步：先做数据验证

在生成看板前，必须验证：

- 数据来源是正式、测试还是模拟。
- 日期范围和截止日期是否正确。
- 样本量是否符合业务预期。
- 核心字段是否缺失。
- 重复数据是否处理。
- 排除前后数量是否能对上。
- 页面展示数据是否能追溯到输出数据集。

看板页面不能用“看起来合理”代替数据验证。

## 7. 第五步：复杂看板先做中间表

建议至少准备这些输出数据集：

| 输出数据集 | 用途 |
|---|---|
| KPI汇总表 | 页面核心指标 |
| 趋势表 | 按日/周/月看变化 |
| 结构表 | 区域、渠道、商品、门店、用户构成 |
| 分桶表 | 留存窗口、动销层级、风险等级 |
| 明细表 | 下钻、导出、运营跟进 |
| 排除汇总表 | 解释哪些数据没有进入主分析 |

开发交付时，应说明每张表的粒度、字段、生成逻辑和使用位置。

## 8. 第六步：再设计看板结构

默认页面结构：

```text
全局筛选
-> 数据状态
-> KPI总览
-> 趋势分析
-> 结构分析
-> 漏斗/生命周期/分层
-> 对比分析
-> 明细下钻
-> AI结论摘要
-> 指标释义
```

AI结论必须引用具体计算结果，不能写泛泛建议。

## 9. 第七步：HTML原型必须浏览器验证

交付前检查：

- 页面数据非空。
- 正式/模拟状态显示正确。
- 数据截止日期显示正确。
- 筛选、下钻、导出交互可用。
- 指标说明能被看到。
- 图表、表格和文字不重叠。
- 页面数据和输出数据集一致。

## 10. 开发交付物

一个合格的看板类交付包至少包含：

- 原始需求和确认问题
- 业务问题定义
- 字段盘点和表粒度判断
- 指标口径字典
- 数据验证报告
- 数据处理逻辑、SQL或脚本说明
- 输出数据集说明
- 看板结构说明
- 单文件HTML看板
- 浏览器验证记录
- 开发注意事项

## 11. 给Codex的执行口令

```text
请按看板类产品经理执行SOP处理这个需求。

不要直接生成页面。
先从业务问题、使用人、看完后动作、数据源、字段粒度、指标口径和数据验证开始。

如果资料不足，请只问会影响结论和开发交付的关键问题。
如果资料足够，请依次输出：
1. 业务问题定义
2. 字段盘点和表粒度判断
3. 指标口径字典
4. 数据验证方案
5. 输出数据集设计
6. 看板结构说明
7. HTML看板生成计划
8. 开发交付清单
```
