## 3. 需要显式执行的强化规则

### 3.1 指标契约

核心指标不能只写名字，必须写成指标契约：

```text
指标名称：
业务问题：
业务含义：
分子：
分母：
统计粒度：
时间窗口：
日期依据：
去重规则：
补零规则：
排除规则：
聚合规则：
能说明什么：
不能说明什么：
原始数据到结果的例子：
```

### 3.2 口径锁定

业务确认后的口径不能被Codex静默改掉。

如果数据不支持已确认口径，Codex必须说明：

- 当前数据缺什么。
- 原口径为什么无法实现。
- 可以用什么近似口径。
- 近似口径不能代表什么。

### 3.3 看板模块自解释

每个看板模块都必须回答三件事：

```text
这个模块看什么
当前数据说明什么
业务应该怎么用
```

### 3.4 浏览器级质量检查

交付HTML看板前必须检查：

- 页面能打开。
- 关键数据非空。
- 筛选、点击、下钻、悬浮提示可用。
- 没有控制台错误。
- 没有横向溢出。
- 长文本、大数字、空状态不破坏布局。
- 口径说明、单位、截止日期、正式/模拟状态可见。

### 3.5 原始数据追溯

对于生命周期、分层、热力图、漏斗、质量标签等复杂分类，至少随机追溯3-5个对象：

```text
原始记录
-> 清洗结果
-> 中间表
-> 分桶/分类
-> 页面展示
```

### 3.6 恢复模式

当用户反馈“看不懂、不合理、太假、没检查、不是之前说的”时，Codex必须进入恢复模式：

1. 先用业务语言复述问题。
2. 判断是口径问题、数据问题、可视化问题还是交互问题。
3. 回到已确认的指标契约。
4. 做最小修改。
5. 重新浏览器验证。
6. 说明改了什么、验证了什么。

## 4. 不直接暴露给产品经理的原因

`date-fenxi-skills` 是给Codex执行的能力说明，不是给产品经理阅读的操作手册。

产品经理需要的是：

- 一句话启动。
- 被Codex一步步问问题。
- 给资料。
- 看Codex判断资料是否合格。
- 看Codex输出分析和看板。

所以本包采用“前台简单、后台严格”的方式：

```text
产品经理只看开始入口
Codex按完整数据分析规则执行
管理者用团队试跑流程复盘
```
