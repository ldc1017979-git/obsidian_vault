# 大批次查询需求测试与原型问题复盘能力提升报告

生成日期：2026-07-10  
对象：大批次查询功能-数智工厂前端交互页面  
目标：复盘本次从一句话需求到前端交互页面产出的全过程，沉淀需求测试、问题纠偏、原型验证和后续自检规则，避免同类查询需求再次出现理解偏差、页面口径不一致或交付物不同步。

## 一、总体结论

本次需求的核心问题不是单个页面样式是否还原，而是“一句话需求”在逐步收敛过程中，必须先把查询对象、数据来源、页面入口、字段口径、权限规则和视觉基线全部锁定。

最关键的纠偏是：大批次查询不是查询截图、图片或本地文件资料，而是查询系统中所有填写过该大批次号的表单记录。

本次已完成的主要判断包括：

- 端口归属：工厂端。
- 承载系统：数智工厂现有系统内新增查询能力。
- 查询对象：系统表单记录，不是附件或图片。
- 核心条件：大批次号必填、精确匹配。
- 结果形态：按目标页面调整为高密度单表格平铺展示。
- 查看逻辑：点击“查看”进入原系统表单详情页。
- 权限逻辑：详情查看权限继承原表单权限。
- 视觉基线：继承数智工厂系统壳、顶部导航、左侧菜单、Tags-View、Element Plus 风格表单和表格。

本次暴露出的主要不足是：早期需求对象没有一次性锁死，导致页面结构、字段命名和日期筛选口径出现过多版本。后续同类需求必须先做“查询对象确认”和“现有系统截图基线确认”，再进入 PRD 和原型。

## 三、做得不好的地方

### 1. 没有最早锁死“查询对象”

本次最开始只知道“新增大批次查询功能”，但我没有先把查询对象拆成可选项让产品经理确认，例如：

- 查询系统表单记录。
- 查询附件或图片资料。
- 查询单据台账。
- 查询追溯关系。
- 查询统计结果。

后果是早期容易把文件夹截图理解成资料包查询，偏离了真正需求。

改进规则：

- 所有“查询类需求”必须先确认查询对象。
- 用户提供截图时，要先判断截图是数据来源、页面基线、业务举例，还是结果样例。
- 没有确认查询对象前，不生成页面结构和字段清单。

### 2. 过早形成分组展示假设

早期页面按“表单名称分组/折叠”来组织结果，逻辑上能解释，但与用户后来提供的目标图不一致。目标图明确是单表格平铺展示，且强调后台高密度查询效率。

后果是如果不及时回收旧假设，研发可能误以为需要做分组、折叠、表单聚合统计等额外能力。

改进规则：

- 目标截图出现后，目标截图的页面结构优先级高于早期假设。
- 若截图与旧原型冲突，必须明确标注“旧口径废弃/待确认/需同步”。
- 查询页默认优先高密度表格，只有用户明确要求聚合视图时再做分组。

### 3. 字段口径没有第一时间贴合系统术语

早期字段使用“表单名称、订单号、状态、提交人”等通用描述。目标图中实际使用的是“工序/表单名称、单据号、原状态、操作人、提交时间”等更贴近数智工厂系统的字段。

后果是字段口径不一致会影响 PRD、接口字段映射、前端列名和研发理解。

改进规则：

- 现有系统截图中的字段名优先级高于我自行整理的通用字段名。
- 字段表必须区分“业务含义”和“页面展示名”。
- 跨表单查询必须补一张字段映射表，说明不同表单字段如何统一到查询列表列名。

### 4. 日期筛选口径没有及时设为冲突项

过程中出现过“生产日期范围”为非必填的需求补充，但目标页面截图展示的是单个生产日期。两者都可能合理，但代表不同筛选能力。

后果是如果直接按某一版实现，会造成产品、前端和研发口径不一致。

改进规则：

- 当用户补充需求与目标图不一致时，必须立刻标记为“冲突待确认”。
- PRD 中要写清楚最终采用单日期、日期范围，还是支持起止日期。
- 研发联调前必须确认生产日期筛选对应字段：生产日期、填报日期、单据日期，还是提交时间。

### 5. 权限继承规则需要更早前置

用户明确提出“有哪些权限可以点击详情按钮进入到该表单详情页面”。这说明跨表单查询页不是一个独立权限孤岛，而是要连接原表单详情权限。

后果是如果只做一个“查看”按钮，不说明权限来源，研发可能新增一套不必要或错误的权限规则。

改进规则：

- 跨表单查询结果中的“查看”默认继承原表单详情权限。
- 查询页权限和详情页权限要分开描述：能查到不一定能查看详情。
- 无权限时要确认是隐藏记录、置灰按钮、提示无权限，还是字段脱敏展示。

### 6. 交付物同步不够及时

本项目已经形成多个交付物：PRD、产品确认原型、开发实现原型、最终 UI 视觉稿、页面差异总结、新前端交互页面和本复盘报告。最新页面已经按目标图重构，但早期文档和原型仍保留部分旧口径。

后果是产品确认、开发实现和后续测试可能引用不同版本，造成重复沟通。

改进规则：

- 每次页面结构发生大变更后，必须执行“交付物同步清单”。
- 最新有效口径必须写入一个“当前生效版本”说明。
- 旧原型如果保留，必须标注“早期版本，不作为开发依据”。

### 7. QA 不应只验证页面能打开

对于前端交互页面，不能只确认 HTML 能打开、按钮能点。查询页必须验证输入、筛选、重置、无结果、权限提示、查看入口、开发备注和敏感信息。

后果是页面看起来完整，但实际交互链路可能无法支撑产品确认或开发理解。

改进规则：

- 所有可点击控件必须有真实结果。
- 查询条件必须参与列表筛选或状态变化。
- 开发备注必须能打开、关闭，且不遮挡主业务流程。
- 交付前必须扫描敏感词、账号、密码、token 和真实登录链接。

## 四、后续必须执行的自检清单

### 1. 需求对象自检

- 这次查询查的是什么对象：表单记录、附件、台账、统计指标，还是追溯链路。
- 数据来源是否来自系统表单，而不是截图或本地资料。
- 大批次号是主查询条件，还是与物料、单据、批号组合查询。
- 是否需要查询全部状态，还是只查已提交、已审核等正式状态。

### 2. 资料审计自检

- 用户提供的每张截图是页面基线、业务举例、字段样例，还是结果样例。
- 现有系统链接或截图是否已提取顶部导航、左侧菜单、Tags-View、表单、表格和按钮风格。
- 表单资料是否仅用于识别表单范围，不被误当成附件查询对象。
- 资料中明确可见、基于推断、待确认三类内容是否分开记录。

### 3. 页面结构自检

- 页面入口是否为生产管理 / 过程管理 / 大批次查询。
- 是否保留数智工厂系统壳、顶部导航、左侧菜单和标签页。
- 查询区是否只放必要条件，避免做成复杂报表页。
- 结果区是否按最新确认采用单表格平铺。
- 是否有当前查询摘要和记录数。

### 4. 字段口径自检

- 列名是否使用目标页口径：工序/表单名称、单据号、大批次号、产线、班次、班组、原状态、生产日期、操作人、提交时间、操作。
- “订单号”和“单据号”是否统一。
- “状态”和“原状态”是否统一。
- “提交人”和“操作人”是否统一。
- 跨表单字段是否需要研发提供映射表。

### 5. 查询交互自检

- 大批次号为空点击搜索，是否提示必填。
- 输入有效大批次号后，是否展示匹配结果。
- 产线、班组、班次、生产日期是否参与筛选。
- 重置是否清空查询条件和查询结果。
- 无结果时是否有明确空态提示。
- 当前查询摘要是否随筛选条件变化。

### 6. 权限自检

- 查询页是否有查看入口权限。
- 查看原表单详情是否继承原表单权限。
- 无权限记录是否显示。
- 无权限“查看”是置灰、隐藏，还是点击后提示。
- 无权限时字段是否完整展示，是否需要脱敏。

### 7. 状态标签自检

- 是否覆盖填写中、已提交、已审核。
- 是否还需要草稿、驳回、作废、撤回、已关闭等状态。
- 状态颜色是否符合现有系统习惯。
- 原状态是否来自原表单，不由查询页重新计算。

### 8. 交付物同步自检

- 最新页面是否为 `06-前端交互页面-大批次查询.html`。
- `01-PRD页面说明-大批次表单查询.md` 是否同步最新字段和页面结构。
- `02-04` 早期原型是否继续保留，还是标注为早期版本。
- `05` 页面差异总结是否与最新页面结论一致。
- 本文档是否只做复盘，不替代正式 PRD。

### 9. 敏感信息自检

- 不保存真实登录链接。
- 不保存账号、密码、token。
- 不出现测试账号名称。
- 不把内部环境信息写入开发交付说明。
- 原型顶部用户信息使用“测试用户”或通用占位。

### 10. QA 自检

- HTML 语法和 JS 运行无错误。
- 搜索、重置、查看、开发备注按钮可用。
- 筛选条件改变后列表或摘要有变化。
- 无结果状态可触发。
- 权限提示可触发。
- 表格列宽不拆字、不重叠。
- 页面在常见桌面宽度下不出现明显错位。

## 五、后续生成同类查询页面的工作方法

### 第一步：先确认查询对象

不要先画页面。先确认“查什么”：

- 查表单记录。
- 查单据台账。
- 查附件资料。
- 查追溯链路。
- 查统计结果。

只有查询对象确认后，字段、权限、数据来源和接口方案才有意义。

### 第二步：再确认系统承载和入口

如果是现有系统内新增功能，必须先确认：

- 一级导航。
- 左侧菜单。
- Tags-View。
- 页面路径。
- 同类页面风格。
- 是否需要继承现有权限体系。

### 第三步：建立字段映射和状态口径

跨表单查询必须把不同表单字段映射到统一列表字段：

- 表单名称或工序名称。
- 单据号。
- 大批次号。
- 产线。
- 班次。
- 班组。
- 原状态。
- 生产日期。
- 操作人。
- 提交时间。

### 第四步：确认查询条件和结果形态

查询条件要区分：

- 必填条件。
- 非必填条件。
- 精确匹配。
- 模糊匹配。
- 单日期。
- 日期范围。
- 枚举选择。

结果形态要区分：

- 单表格平铺。
- 按表单分组。
- 按工序分组。
- 按状态统计。
- 支持导出或分页。

### 第五步：补齐权限和异常

至少确认：

- 能查询的人。
- 能查看详情的人。
- 无权限怎么显示。
- 无结果怎么提示。
- 字段缺失怎么展示。
- 原表单已删除或作废怎么处理。

### 第六步：最后生成原型和同步文档

原型生成后必须同步：

- PRD 页面说明。
- 字段表。
- 交互矩阵。
- 开发备注。
- 待确认事项。
- QA 结果。

## 六、可复用的 Codex 自我约束指令

后续处理同类“查询类后台页面”时，应默认执行以下约束：

```text
1. 用户只说“新增查询功能”时，先确认查询对象，不直接生成页面。
2. 用户提供截图时，先判断截图角色：页面基线、业务举例、字段样例或结果样例。
3. 不把表单照片、文件夹截图误认为系统要查询的附件对象。
4. 现有系统截图中的导航、菜单、字段名和表格结构优先于我的早期假设。
5. 页面结构一旦从分组改为平铺，必须同步标记旧原型口径废弃或待更新。
6. 跨表单查询必须说明字段映射、状态来源和原表单详情跳转。
7. 查询页权限和详情页权限必须分开描述，详情权限默认继承原表单。
8. 日期条件出现单日期和日期范围冲突时，必须列为待确认项。
9. 交付前必须检查搜索、重置、查看、无结果、无权限、开发备注是否都有真实交互。
10. 交付物中不得保存真实登录链接、账号、密码、token 或测试账号信息。
```

## 八、最终总结
