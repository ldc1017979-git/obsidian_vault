# 产品经理工作流与原型生成问题清单

生成日期：2026-07-10  
来源项目：大批次表单查询项目  
记录目的：沉淀本轮写作、需求测试总结和前端交互页面生成过程中 Codex 暴露的问题，作为后续修正产品经理多端口工作流、引导方式、原型生成能力和交付验证规则的依据。

## 一、我先判断这是什么类型的反馈

- 反馈类型：工作流复盘 / 产品需求测试反馈 / 原型生成能力改进反馈。
- 不是：单纯文档润色、单个 HTML 页面修复、单个字段调整。
- 本轮应该产出的内容：问题清单、问题分类、根因分析、需要同步的工作流规则、下一轮验证安排。

本轮反馈的核心不是“大批次查询页面还原得像不像”，而是 Codex 在从一句话需求到总结文档的过程中，暴露出了一些通用能力缺口：

- 需求对象锁定不够早。
- 页面基线确认后，旧交付物没有自动同步。
- 写总结时容易先写过程流水账，而不是按“问题复盘 + 能力提升”口径沉淀。
- 原型生成和 PRD 文档之间缺少版本生效规则。
- 对冲突项的标记不够敏感，例如“生产日期范围”和目标图单日期之间的冲突。

## 二、本轮暴露的问题

| 问题类型 | 暴露问题 | 具体表现 | 影响 |
|---|---|---|---|
| 任务识别问题 | 没有第一时间识别用户要的是“需求测试复盘”口径 | 先生成了偏页面还原的总结，用户又要求改成从一开始到出页面的需求测试总结 | 增加返工，说明总结文档类型识别不够准 |
| 反馈处理问题 | 对“按照某报告方式重写”理解为结构仿写，但还需要更明确复用其复盘深度 | 后续才按“总体结论、问题记录、做得不好、自检清单、方法沉淀”重写 | 说明 Codex 需要建立报告模板识别和迁移规则 |
| 需求对象问题 | 查询对象锁定偏晚 | 用户提供表单截图后，曾存在误解为图片/附件查询的风险 | 容易把系统记录查询做成资料包查询 |
| 引导问题 | 对冲突需求没有立即挂起为待确认 | 用户曾要求生产日期范围，目标图又是单日期 | 可能造成 PRD、原型、研发接口口径不一致 |
| 页面基线问题 | 目标截图出现后，旧原型和旧 PRD没有自动标记为早期版本 | `01-04` 仍可能保留旧字段、旧结构或分组展示思路 | 多版本并存，开发容易引用错文件 |
| 原型生成问题 | 早期结果形态存在过度设计倾向 | 曾按表单名称分组，而目标图是单表格平铺 | 查询页复杂度可能被放大 |
| 字段口径问题 | 字段展示名没有完全以目标系统截图为最高优先级 | 早期用了“订单号、状态、提交人”等通用字段 | 影响字段映射和开发理解 |
| 权限表达问题 | 权限继承规则后置 | 用户追问后才明确“查看详情继承原表单权限” | 跨表单查询容易形成错误权限模型 |
| QA 问题 | 验证重点容易停留在文件生成和结构存在 | 需要更强制地验证搜索、重置、查看、无结果、无权限、开发备注 | 页面可看但不一定可作为开发理解依据 |
| 敏感信息问题 | 原型中曾出现测试账号字样 | 后续扫描并替换为通用“测试用户” | 说明交付前敏感信息扫描必须前置为固定门禁 |
| 写作问题 | 总结文档初版偏过程记录，不够像能力提升报告 | 用户明确要求“需求测试总结”，并指定参考积分管理复盘报告 | 说明总结类交付物需要先判断文档用途和读者 |

## 三、根因分析

### 1. 查询类需求缺少强制的“查询对象确认门禁”

当前工作流强调端口、资料、承载系统，但对“查询类需求”的第一判断还不够强制。  
本轮大批次查询说明：只说“新增查询功能”时，Codex 必须先确认查的是表单记录、附件、台账、指标、追溯链路还是其他对象。

需要补强：

- 在工作流中新增“查询类需求对象确认卡”。
- 将“查询对象未确认，不进入字段表和原型设计”设为门禁。
- 对用户提供的截图，强制判断其角色：页面基线、数据来源、业务举例、字段样例、结果样例。

### 2. 目标截图优先级规则不够明确

目标截图出现后，应该自动提升为页面结构和视觉基线的最高证据之一。  
本轮早期已有分组展示原型，但目标图明确是单表格平铺，此时需要立即标记旧口径。

需要补强：

- 目标截图与旧原型冲突时，Codex 必须输出冲突表。
- 明确哪些旧结论废弃、哪些保留、哪些待确认。
- 最新页面确认后，自动提出“是否同步 PRD 和旧原型”的下一步。

### 3. 文档类型识别不够细

“总结文档”至少可能有三种：

- 页面还原差异总结。
- 需求测试全过程总结。
- 问题复盘与能力提升报告。

本轮用户明确指出不需要页面还原总结，而要从一开始到出页面的需求测试总结。后续又要求按积分管理复盘报告方式重写。说明 Codex 在写总结前应先判断文档类型，而不是默认写成一般总结。

需要补强：

- 新增“总结类文档类型判断”规则。
- 写总结前先说明：本文是页面差异、需求测试、开发交付复盘，还是能力提升报告。
- 如用户提供参考报告，必须提取其结构、语气、深度和用途，再迁移到当前项目。

### 4. 冲突项没有形成自动待确认机制

本轮“生产日期范围”和目标图单日期就是典型冲突。  
这类冲突不一定要立刻解决，但必须明确写入待确认，而不是在不同交付物中各写一版。

需要补强：

- 发现新输入与旧结论冲突时，自动输出“冲突项登记”。
- 冲突项必须进入 PRD 待确认和开发备注。
- 冲突未解决时，不得写成已确认规则。

### 5. 交付物版本同步机制不足

项目过程中形成了多个交付物：PRD、产品确认原型、开发原型、视觉稿、差异总结、新前端页面、需求测试总结。  
当最新前端页面已经变化时，旧文档如果不标注版本状态，会影响后续使用。

需要补强：

- 每个项目目录增加“当前生效交付物说明”。
- 页面结构变化后，Codex 必须检查哪些文件需要同步。
- 旧原型继续保留时，必须标注“早期版本，不作为开发依据”。

### 6. 原型 QA 与业务结果验证仍需加强

当前工作流已经要求不能只验证按钮可点，但执行时仍容易只做结构检查。  
查询页尤其需要验证：输入条件是否参与筛选、重置是否清空、无结果是否出现、无权限是否提示、查看是否能表达详情跳转。

需要补强：

- 查询类原型增加固定 QA 用例。
- 开发备注必须覆盖数据来源、字段映射、权限、状态、异常和待确认项。
- QA 结果不能写“全部通过”，除非确实逐项验证。

## 四、需要同步的工作流规则

### 1. 建议同步到 `01-Codex自动引导总入口-多端口产品工作流.md`

建议新增规则：

- 当用户要求“总结、复盘、测试全过程、能力提升报告”时，先判断文档类型，不直接按普通项目总结输出。
- 当用户给出测试反馈、复盘要求或“后续修正工作流”时，默认进入工作流复盘模式。
- 查询类需求必须先确认查询对象。
- 新资料与旧结论冲突时，必须建立冲突项登记。

### 2. 建议同步到 `08-端口分流与资料引导卡.md`

建议新增规则：

- 资料盘点后增加“资料角色判断”：截图是页面基线、业务举例、字段样例、结果样例，还是数据来源。
- 查询类需求增加对象选项：表单记录、附件资料、台账、指标、追溯链路、其他。
- 用户提供目标截图后，截图结构优先于早期假设，但仍需标出待确认冲突。

### 3. 建议同步到 `09-现有系统链接反推设计规范完整性清单.md`

建议新增规则：

- 如果目标截图只覆盖单页面，不能把它扩展为全系统规范，但可以作为当前页面最高优先级基线。
- 反推规范输出时必须标注“当前页面明确可见”和“早期原型不一致点”。
- 目标截图与已生成原型冲突时，必须输出差异回收清单。

### 4. 建议同步到原型生成门禁

建议新增规则：

- 生成新原型前必须确认：当前原型是产品确认版、开发实现版、最终 UI 视觉稿，还是目标图还原版。
- 生成新原型后必须检查：是否需要同步 PRD、旧原型、字段表、交互矩阵和开发备注。
- 原型中不得保存真实登录链接、账号、密码、token；测试用户信息必须通用化。

### 5. 建议新增一个通用文件

建议新增：

- `查询类需求引导与原型自检清单.md`

建议覆盖：

- 查询对象确认。
- 查询条件确认。
- 字段映射确认。
- 状态来源确认。
- 权限继承确认。
- 无结果、无权限、字段缺失、性能和分页。
- 查询、重置、查看、导出、开发备注 QA。

## 五、下一轮团队测试安排

### 1. 测试目标

验证 Codex 是否能在新项目中稳定执行：

- 先判断反馈类型。
- 先确认查询对象。
- 先识别资料角色。
- 冲突项不自行拍板。
- 目标截图出现后自动回收旧原型口径。
- 总结文档能按用户指定类型输出。

### 2. 测试样本

建议下一轮至少准备 3 类样本：

| 样本 | 测试目的 |
|---|---|
| 查询类需求 | 验证是否先确认查询对象和字段映射 |
| 现有系统新增模块 | 验证是否继承系统壳、菜单、组件和权限 |
| 总结/复盘类请求 | 验证是否先判断文档类型和复盘口径 |

### 3. 测试角色

- 产品经理：提供一句话需求、截图和纠偏反馈。
- 业务代表：确认业务对象、字段和状态。
- 研发代表：确认数据来源、接口字段、权限和性能。
- 测试代表：按交互矩阵验证页面行为。

### 4. 反馈口径

每条反馈建议按下面格式记录：

| 反馈项 | 说明 |
|---|---|
| 发生阶段 | 端口分流 / 资料审计 / 需求确认 / PRD / 原型 / QA / 总结 |
| 反馈内容 | 用户或测试人员实际指出的问题 |
| 问题类型 | 引导问题 / 需求理解问题 / 页面基线问题 / 原型问题 / QA 问题 / 写作问题 |
| 影响 | 会误导产品、研发、测试还是业务 |
| 是否需要同步工作流 | 是 / 否 |
| 建议同步位置 | 入口规则 / 资料引导卡 / 反推规范 / 原型门禁 / QA 清单 |

### 5. PASS / REVIEW / FAIL 标准

| 结果 | 判定标准 |
|---|---|
| PASS | Codex 能识别任务类型，完成必要门禁，输出内容无需结构性返工 |
| REVIEW | 方向正确，但有局部漏项、冲突项或交付物同步问题 |
| FAIL | 跳过关键门禁、误解查询对象、未读资料就生成最终原型，或把未确认内容写成已确认 |

## 六、本轮可直接转成规则的结论

1. 查询类需求必须先确认“查询对象”，不能先画页面。
2. 截图必须先判断资料角色，不能把业务举例误认为数据来源。
3. 目标截图出现后，页面结构优先级高于早期原型假设。
4. 新输入与旧结论冲突时，必须建立待确认项。
5. 总结文档要先判断类型：页面差异、需求测试、能力提升、开发交付复盘。
6. 生成新原型后，必须检查旧 PRD、旧原型和交互矩阵是否需要同步。
7. 交付物中不能保存真实登录链接、账号、密码、token 或测试账号信息。
8. QA 不能只验证页面打开和按钮点击，必须验证业务结果。
