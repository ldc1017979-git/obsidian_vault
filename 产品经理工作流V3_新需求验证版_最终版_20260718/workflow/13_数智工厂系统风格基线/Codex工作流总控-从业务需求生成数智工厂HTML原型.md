# Codex 工作流总控：从业务需求生成数智工厂 HTML 原型

用途：这是后续真实项目使用的总控指令。目标不是让 Codex 根据旧 HTML 改版，而是让 Codex 在读取数智工厂基准后，仅凭业务需求 / PRD / 产品说明，生成符合现有系统风格和交互规范的 HTML 原型。

## 0. 测试反馈与工作流复盘优先级

当用户提供的是测试反馈、团队产品测试结果、试跑报告、复盘意见，或明确要求“同步到工作流”时，本文件的执行目标从“生成数智工厂 HTML 原型”切换为“产品工作流复盘与规则更新”。

此时 Codex 必须先判断反馈类型：

| 反馈类型 | 处理方式 |
|---|---|
| 原型缺陷反馈 | 修正原型、补 QA、同时沉淀规则 |
| 团队产品测试反馈 | 输出测试复盘、问题归类、下一轮安排，并同步通用工作流 |
| 工作流试跑反馈 | 更新入口、门禁、反馈表、专项检查清单 |
| 交付质量反馈 | 输出整改清单、重新验收结果和风险说明 |

禁止把团队测试反馈一律当成“继续修 HTML”。如果用户没有明确要求先修页面，默认优先产出：

- 测试复盘。
- 工作流修正规则。
- 需要同步的源文件清单。
- 下一轮团队测试 SOP。

完成规则同步后，再视需要处理具体原型。

## 1. 工作流目标

输入：

- 数智工厂系统基准文件夹。
- 当前业务需求、PRD、产品说明或字段/流程描述。
- 可选：竞品截图、已有草稿、旧 HTML。可选材料只能作为参考，不能作为必须输入。

输出：

- 一个可打开的单文件 HTML 原型。
- HTML 内嵌 CSS 和 JS。
- 不依赖外部接口。
- 使用模拟数据。
- 页面可点击切换。
- 符合数智工厂系统壳、组件风格、布局密度、页面层级和交互规范。
- 内置开发可主动打开的“开发备注 / 逻辑说明 / 字段说明”入口，方便研发在 HTML 内查看关键字段和规则；该入口不替代 PRD。

## 3. 关键原则

### 3.1 不依赖旧 HTML

真实项目中，Codex 不能要求用户必须提供旧 HTML。旧 HTML 只能用于复盘和对比，不是生成新原型的必要条件。

正确流程是：

`业务需求 -> 冻结业务硬约束 -> 匹配数智工厂信息架构 -> 套用系统壳和组件规范 -> 生成 HTML -> QA`

### 3.2 只取形，不取业务

数智工厂基准提供的是系统规范，不是具体业务模板。

可以继承：

- 后台系统壳。
- 左侧菜单。
- 顶部业务域导航。
- Tags-View。
- 浅灰背景和白色内容区。
- Element Plus 风格组件。
- 高密度表格和表单。
- 列表、新增、编辑、详情、配置、报表、看板、审批流、日志、附件等页面组织方式。
- 按钮颜色语义。
- 风险动作二次确认。

不可以继承：

- 无关测试案例中的业务字段。
- 无关测试案例中的状态流转。
- 无关测试案例中的业务动作。
- 无关测试案例中的业务流程。

如果业务逻辑和系统风格适配冲突，以业务逻辑为准，再用数智工厂组件承载。

## 4. 生成前硬性步骤

Codex 在写 HTML 前，必须先完成以下判断。

### 4.0 需求成熟度与建模门禁

如果用户输入不是完整 PRD，而是“一句话需求、初步想法、流程图、口头说明、旧截图、会议纪要”等未结构化资料，Codex 不得直接生成 HTML。必须先完成以下产物，并写入项目过程记录或本次回答的“生成前确认”部分：

- 需求定义卡片（RDD）：必须包含真实痛点、JTBD、用户故事、验收标准、NFR、MVP/理想方案、影响范围、成功指标。
- 调研完整性检查：至少覆盖业务背景、现状痛点、目标、业务场景、数据与规则、权限与协同六个维度；缺口必须标记为“待确认”或“研发待确认”，不得伪装成已确认。
- 字段清单：按核心业务对象输出主表/明细字段、类型、必填、默认值、来源、校验、枚举、计算规则、关联关系和 TypeScript/Mock 数据形状。
- 业务流程推演：输出主流程、异常流程、状态机、数据变化过程、边界场景、异常场景、影响范围。
- 规则总表：每条业务规则必须编号，包含触发条件、处理逻辑、例外情况、冲突处理、是否配置化。
- 页面与交互规格：逐页列出查询区、功能区、列表区、详情/表单、状态-操作映射、空态/异常态/边界态。
- 验收用例草案：基于 RDD 的 AC、流程边界和页面交互，列出 P0/P1/P2 验收路径。

只有上述信息足以冻结核心对象、字段、状态、流程、权限、异常和验收标准时，才允许进入 HTML 生成。

如果用户明确要求“先快速生成原型”，也必须在生成前列出：

- 本次采用的暂定假设。
- 哪些内容未确认。
- 未确认项对原型可信度的影响。

最终回答不得把“暂定假设版”说成“开发可直接实现版”。

### 4.1 判断项目类型

必须说明本次属于：

- 成熟系统新增模块。
- 旧模块改造。
- 独立新产品。
- 固定回归测试。

如果是成熟系统新增模块，默认必须嵌入数智工厂系统壳。

### 4.2 冻结业务硬约束

必须先列出：

- 核心业务对象。
- 业务对象矩阵。
- 角色权限矩阵。
- 状态矩阵。
- 动作矩阵。
- 页面清单。
- 可见菜单页。
- 隐藏新增页。
- 隐藏编辑页。
- 隐藏详情页。
- 弹窗/抽屉使用边界。
- 角色权限。
- 状态机。
- 审批、确认、申诉、撤回、作废、删除等动作规则。
- 明确不做范围。

没有冻结业务硬约束，不允许直接生成 HTML。

对于现有系统新增模块，业务矩阵必须至少回答：

| 矩阵 | 必须回答 |
|---|---|
| 业务对象矩阵 | 有哪些对象，例如申请单、核销单、规则、福利、明细 |
| 角色矩阵 | 管理员、员工、审批人、人事等分别能做什么 |
| 状态矩阵 | 草稿、待审批、通过、驳回、待确认、已确认、申诉中、已核销等 |
| 动作矩阵 | 新增、编辑、提交、撤回、审批、确认、申诉、作废、删除、导出 |
| 页面矩阵 | 哪些是一级菜单页，哪些是隐藏新增/详情/编辑/申诉页 |

### 4.3 映射信息架构

必须写出菜单路径：

`一级业务域 > 二级业务子域 > 业务组 > 页面`

如果没有完全匹配的现有菜单，应选择最接近的业务域，并说明推断依据。

### 4.4 选择页面类型

必须为每个页面标注类型：

- 标准列表页
- 新增页
- 编辑页
- 详情页
- 记录/检查表页
- 报表/台账页
- 基础资料/配置页
- 流程审批页
- 数据看板页
- 知识/文件页

## 5. HTML 生成规范

### 5.1 系统壳

必须包含：

- 左侧菜单，约 210px。
- 顶部业务域导航。
- Tags-View 页签。
- 主内容浅灰背景。
- 白色内容区。
- 当前业务域激活态。

### 5.2 组件

必须使用接近 Element Plus 的：

- 按钮
- 输入框
- 选择器
- 日期范围
- 表格
- 分页
- Tabs
- 上传
- 状态标签
- Dialog
- Drawer

### 5.3 页面打开方式

默认规则：

- 新增、编辑、详情、申诉、审批详情：独立页面 / Tags-View。
- 删除、撤回、作废、员工确认、风险动作：二次确认弹窗。
- 选择人员、选择物料、批量选择、轻量配置：弹窗或抽屉。

复杂业务流程不得塞进小弹窗。

### 5.4 按钮语义

- 蓝色：搜索、提交、确认、导入、主流程。
- 绿色：新增、添加、创建。
- 黄色：编辑、警示。
- 红色：删除、作废、危险操作。
- 灰色：取消、重置、普通操作。

### 5.4A 开发备注与逻辑说明

开发实现原型必须提供一个开发可主动打开的说明入口，命名可使用“开发备注”“逻辑说明”“字段说明”或同等含义。入口可采用浮动按钮、侧边抽屉、折叠面板、右侧说明栏或独立 Tab，但不得遮挡主业务流程，不得把说明文案常驻成汇报页。

说明内容至少包括：

- 页面用途和核心业务逻辑。
- 字段解释：字段名、含义、来源、必填、校验、枚举、默认值、计算规则、关联关系。
- 状态流转：状态含义、进入条件、可执行动作、下一状态、异常出口。
- 操作结果：按钮触发条件、执行结果、当前页反馈、返回列表同步。
- 权限差异：角色、可见页面、可执行动作、数据范围、状态限制。
- 数据来源和 Mock 说明：Mock 数据字段、样例覆盖状态、正式接口待确认项。
- 异常、空态、边界规则和校验提示。
- 待确认事项、研发待确认事项和 PRD/页面说明引用。

PRD、字段清单、规则表和页面说明仍作为正式源文档保留；HTML 内备注只做开发走读辅助。看板类页面还必须包含指标口径、统计粒度、数据来源、筛选联动、下钻路径和刷新规则。

### 5.5 单文件 HTML 代码组织硬要求

单文件 HTML 原型必须具备可检查、可维护的前端实现结构：

- 使用统一 `state` 对象管理数据、筛选、分页、当前页面、当前单据、弹窗、加载、错误、空态、权限等状态。
- 使用统一 `render()` 或页面级渲染函数更新界面，不得把关键业务状态散落在不可追踪的 DOM 文案里。
- 列表、详情、表单、配置、排行榜等页面必须从同一批 Mock 数据派生，避免列表和详情各写一套假数据。
- 可见按钮必须从状态-操作矩阵生成或校验，不能靠静态按钮堆叠。
- 事件处理优先使用事件委托，新增数据后仍能点击。
- 用户输入渲染到页面前必须做基础转义，表单必须有类型、范围、长度和必填校验。
- Mock 数据原则上不少于 20 条，且覆盖主要状态、边界值、异常值和不同角色/部门。
- 必须提供或显式说明 Loading、Empty、Error、No Permission 四类状态；如果缺失，QA 中必须列为未通过或降级项。
- 弹窗/抽屉/下拉必须支持 Esc、点击外部、关闭按钮、取消按钮、焦点进入和焦点回收；未实现时不得写“可访问性交互通过”。

## 6. 生成后 QA

Codex 交付前必须完成以下检查。

### 6.1 业务一致性检查

- 页面是否覆盖核心业务路径。
- 状态机是否正确。
- 按钮是否按状态出现。
- 角色权限是否合理。
- 新增、编辑、详情、申诉是否按页面打开。
- 风险操作是否二次确认。

### 6.2 系统风格检查

- 是否保留数智工厂系统壳。
- 是否保留 Tags-View。
- 是否使用浅灰背景和白色内容容器。
- 是否符合 Element Plus 后台组件风格。
- 是否保持高密度表格/表单。
- 是否避免营销页、大 hero、暗黑大屏、装饰型视觉。
- 是否对照真实系统截图检查系统壳、左侧菜单、顶部导航、Tags、表格、表单、按钮、分页，而不是只凭文字规范判断。
- 顶部通知、上传、全屏等工具入口不得使用 `铃`、`云`、`全` 这类纯文字占位；应使用图标或接近真实系统的图标按钮。
- 左侧菜单宽度、Logo 区、菜单项高度和激活态应接近真实系统基线；不得用明显不同的窄栏结构冒充系统壳，除非基线就是该结构。
- 配置页应对照真实设置页：新增类动作使用绿色按钮，编辑类动作使用黄色/编辑语义按钮，轻量配置优先弹窗或抽屉。

### 6.3 污染词检查

必须搜索并清理与当前模块无关的旧业务术语。

通用一票否决词：

```text
演示|讲解|DEMO|汇报
```

如果当前模块不是采购模块，还必须排查：

```text
采购单|供应商|采购部门|采购类型|原料|备件|批量添加|下一步|待入库|结算|反审
```

如果当前模块不是商品上下架模块，还必须排查：

```text
上架|下架
```

如果命中，必须说明是否业务确实需要；否则不得交付。

### 6.4 点击路径 QA

至少验证：

- 进入列表页。
- 新增。
- 保存草稿或提交。
- 查看详情。
- 编辑。
- 审批/确认/申诉等核心动作。
- 删除、撤回、作废二次确认。
- 配置新增/编辑。
- 报表/排行榜维度切换。

### 6.5 数据绑定与状态同步硬门禁

以下检查不通过时，不得在最终回答中写“核心路径 QA 通过”：

- 列表任意一行点击“详情”后，详情页必须展示该行对应的单号、员工、状态和关键业务字段。
- 不能只做固定样例详情页；如果详情页未绑定当前行数据，只能说明“页面可打开”，不能说明“详情路径通过”。
- 在详情页执行提交、确认、撤回、作废、删除、审批、申诉处理等动作后，当前详情页状态、底部按钮、操作日志必须同步变化。
- 从详情页返回列表后，列表状态、操作列按钮、分页数据必须与详情页动作结果一致。
- 列表行操作和详情页底部操作必须使用同一套状态机矩阵，不能出现列表收敛、详情页按钮常驻的情况。
- QA 必须区分“页面可打开”“数据绑定正确”“状态流转正确”“当前页刷新正确”，不能把可点击等同于业务通过。
- QA 还必须验证“返回列表同步正确”和“角色权限正确”。
- 点击不同列表行详情时，详情页必须展示当前行对应数据；否则只能说“页面可打开”，不能说“详情通过”。
- 在详情页执行确认、撤回、作废、删除等动作后，当前详情页和返回列表后的状态必须同步；否则状态流转不得写通过。
- 配置、新增、编辑等动作不能只 toast 提示，必须进入真实表单、弹窗、抽屉或页面。
- 新增态必须为空值或占位，编辑态才允许回填历史数据。
- 必须检查桌面、宽表、弹窗/遮罩、新增空态、员工/用户端入口、移动端或窄屏可读性。
- 最终报告中声明已通过的动作，必须在 HTML 中存在可点击入口；未实现的动作不得写入通过结论。

### 6.6 前端交付 QA 硬门禁

交付 HTML 前必须实际打开页面并完成以下检查。任一项失败时，只能说明“待修复”，不能说“前端展示和交互无明显错误”：

- 必须按包外层`14-HTML原型完整测试验收SOP.md`逐项输出覆盖结果，并填写`12-原型真实交互验收记录.md`。
- 浏览器打开 HTML 后，桌面端首屏必须正常显示，不得空白、脚本中断或主内容缺失。
- 捕获并报告 `console.error` 和 `pageerror`；存在脚本错误时不得交付。
- 至少输出并检查这些截图：列表页、新增页、详情页、配置页、移动端列表页。
- Mock 数据原则上不少于 20 条并覆盖多状态；不足时必须说明原因和影响。
- 必须检查 Toast、空态、加载态、错误态；缺失时不得写“状态反馈完整”。
- Dialog/弹窗需检查基础关闭体验：Esc、点击外部关闭、关闭按钮、取消按钮和焦点管理；未实现时必须列为降级项。
- 点击所有可见菜单，确认页面不会空白、错位、内容遮挡或布局破裂。
- 桌面端和移动端都要检查明显横向溢出、文字遮挡、按钮文字挤压、表格操作列不可见等问题。
- 对固定格式页面元素，如表格、分页、底部操作条、Tabs、Dialog，必须设置稳定尺寸和滚动边界，避免点击后布局跳动。
- 对排行榜、图表、指标卡、时间线、审批流等非表格组件，必须检查子元素是否超出父容器、文字/数字是否互相遮挡、图形条/排名标识是否破坏布局。
- 不能只验证“排行榜页面可打开”；必须验证个人/部门、月度/年度切换后排行项仍然显示正常。
- 最终 QA 结果必须列出：视觉基线对照、前端运行错误、桌面截图、移动端截图、核心点击路径、数据绑定、状态同步、污染词。

### 6.7 需求与实现可追溯门禁

生成后的 HTML、测试报告和结论必须能追溯到生成前的业务定义：

- 每个可见菜单页必须能对应页面清单中的页面类型和业务目的。
- 每个列表字段、表单字段、详情字段必须能对应字段清单，不得临时编造无来源字段。
- 每个状态标签和按钮必须能对应状态机或状态-操作矩阵。
- 每个测试通过结论必须对应实际 HTML 中的可点击入口、操作步骤和结果证据。
- 如果最终报告说“覆盖某业务路径”，必须能在 HTML 中完成该路径的实际点击；只展示静态区域不能算覆盖。
- 如果发现实现与 PRD/RDD/过程记录冲突，以已确认业务规则为准修复 HTML；不得修改业务结论去迁就已生成页面。
- 交付物需区分 `drafts/` 草稿、`outputs/` 或项目正式目录中的正式输出；未完成 QA 的 HTML 只能标记为待审版。

### 6.8 开发备注 QA

- HTML 中必须存在开发备注/逻辑说明/字段说明入口，并可打开、关闭或收起。
- 开发备注不得遮挡核心按钮、表格操作列、底部操作条或弹窗主内容。
- 开发备注内容必须与 PRD、字段清单、规则表、权限矩阵和页面说明口径一致。
- 如果备注存在暂定假设或待确认事项，必须明确标记，不能写成已确认规则。
- QA 结论必须单独说明开发备注入口是否通过；未检查时不得写“可交付开发”。

## 7. 最终回答格式

Codex 最终必须说明：

- 已读取哪些基准文件。
- 本次项目类型判断。
- 业务硬约束清单。
- 菜单路径判断。
- 页面类型清单。
- 生成 HTML 路径。
- 核心路径 QA 结果。
- 数据绑定与状态同步 QA 结果。
- 前端交付 QA 结果，包括截图、控制台错误、桌面/移动端展示检查。
- 开发备注/逻辑说明入口 QA 结果。
- 污染词检查结果。
- 未完成或降级项。

只有业务逻辑、页面层级、交互结构、视觉风格和污染词检查都通过，才能说明完成。
