# 事实契约、单一事实源与五维状态规范

> V3新增强制规范。用于解决启动事实冲突、原型阶段后置纠偏、文档残留和多种PASS混称问题。

## 1. 事实优先级与覆盖规则

默认可信顺序：

1. 用户提供的原始业务资料、原始单据和原始页面证据。
2. 用户最新明确确认，并能说明是在补充还是修改旧结论。
3. 当前真实系统、测试环境、截图或操作录屏中可直接观察的事实。
4. 已确认PRD、会议纪要和知识库中的当前有效版本。
5. 个人任务卡、团队测试批次说明。
6. 目录名、文件名和历史样例。
7. Codex通用经验或推荐。

最新确认可以覆盖旧资料，但必须生成决策或变更记录，写清“覆盖了什么、为什么、影响哪些文件”。目录名、任务卡和经验不得覆盖原始资料。不同来源冲突时不得自行挑选方便原型实现的一项。

## 2. 启动冲突表与挂起门

阶段0必须检查产品经理本人、项目名、真实问题、承载系统、是否跨系统、是否关联库存/台账、一期范围和项目终点；业务负责人或研发负责人未知时可登记待确认，不单独阻塞初始资料审计。

| 冲突编号 | 判断项 | 来源A | 来源B | 当前建议 | 需谁确认 | 状态 | 影响 |
|---|---|---|---|---|---|---|---|
| CF-01 |  |  |  |  |  | 待确认/已关闭 |  |

以下任一冲突未关闭时，只能继续读取资料和整理缺口，不得进入正式PRD：

- 产品经理本人、当前全新需求名称或业务原话不能确定。
- 需求解决的问题、承载系统或一期边界相互矛盾。
- “是否联库存、是否跨系统、是否审批、是否影响台账”等会改变对象模型的事实矛盾。
- 当前有效PRD、页面和真实系统指向不同口径，且无法判断哪一个是新版本。

## 3. 项目终点必须在启动时选择

| 终点 | 本轮结束条件 | 不代表 |
|---|---|---|
| 产品方案确认 | 业务目标、范围、对象、规则和页面契约已确认 | 研发可直接开工、真实系统通过 |
| 研发准入 | PRD/AC/页面契约/开发原型与内部QA达到研发接收标准 | 功能已开发、生产性能通过 |
| 真实系统UAT | 已部署功能在真实角色、数据和环境下通过业务场景 | 上线准备完成 |
| 上线准备 | UAT、风险签收、发布、监控、回滚和交接就绪 | 已正式发布 |

项目终点决定必须执行到哪个阶段。不得因为已有HTML就默认终点是研发准入，也不得把产品对原型的签收命名为真实系统UAT。

## 4. 决策预算

- 局部优化：每阶段默认3-6个关键业务决策。
- 常规新模块：每阶段默认5-10个关键业务决策。
- 跨系统或复杂状态项目：不设硬上限，但每6个决策必须形成一次确认稿。
- 客观事实从资料抽取，不做选择题。
- 超出预算时必须说明新增决策来自哪个资料缺口或冲突；能合并的问题一次确认，不拆成多轮单选。
- 同一事实被产品经理纠正两次，立即回到事实来源和名词表，不继续扩展后续问题。

## 7. 单一事实源与原子同步

每类事实只能有一个主档：

| 事实类型 | 主档 | 其他文件如何使用 |
|---|---|---|
| 范围、对象、规则、字段、状态、权限 | 当前有效PRD及其编号附件 | 引用版本和编号，不复制完整旧表 |
| 当前阶段、当前结论、待确认 | 项目过程记录首页 | 其他文件引用，不另建平行首页 |
| 当前有效文件 | 11号版本同步清单 | 交付入口只链接清单中的当前有效项 |
| 实测证据 | 12号验收记录/证据目录 | 反馈表引用测试编号，不自行改写结果 |
| 产品主观体验 | 07号反馈表主观区 | 不能覆盖客观QA结论 |

每次版本升级必须作为一个原子动作同步：当前阶段、当前结论、当前版本、未覆盖项、待确认项、规则/AC统计。任何一项未更新，本次同步为FAIL。

升级后扫描当前有效文件中的：`当前有效`、`待确认`、`未覆盖`、`REVIEW`、`PASS`、旧版本号、已关闭问题。命中不一定是错误，但必须逐条解释或修正；禁止只在文件末尾追加新口径而保留顶部旧结论。

## 8. 五维验收状态

任何收口文件必须同时填写五栏，不得只写裸状态：

| 维度 | 允许状态 | 判定对象 |
|---|---|---|
| 产品确认状态 | 未确认/部分确认/PASS | 范围、规则、页面和产品方向 |
| 内部原型QA状态 | 未测试/REVIEW/PASS/FAIL | 当前有效HTML及内部测试证据 |
| 研发准入状态 | 未评审/有条件/PASS/FAIL | 研发能否据此评估或实现 |
| 真实系统UAT状态 | 未开始/REVIEW/PASS/FAIL/不适用 | 已部署功能的真实场景 |
| 整体项目状态 | 进行中/REVIEW/PASS/FAIL | 相对本轮项目终点的总体结果 |

规则：

- 文件名中的`UAT PASS`只能用于已部署真实系统；产品对原型签收使用“产品确认PASS”。
- “内部QA PASS”不能推导“研发准入PASS”或“整体PASS”。
- 整体PASS必须达到启动时选择的项目终点；其余未开始维度不得被省略。

## 9. 原型和QA专项规则

- 补全示例、模拟审核、切换角色、快速造数等评审辅助动作，只能放在开发/调试面板、开发模式或URL参数中，不得伪装成正式业务按钮。
- 宽表必须在1440×900和1180×800检查左固定区、中间滚动区、右操作区；记录横向滚动前后截图，验证列头/数据对齐、sticky遮挡和返回状态。
- 完整格式身份证号、手机号、邮箱、银行卡号、车牌等即使声称为测试数据，也必须使用明确虚构号码或掩码；无法证明为虚构时判敏感数据扫描FAIL。
- QA报告引用截图、控制台、DOM或脚本结果时，对应文件必须实际存在；只有文字描述不能作为客观PASS证据。

## 10. 新需求验证隔离

- 所有人收到同一个不预设需求的通用包；每位产品经理必须从自己当前工作中选择一个真实全新需求，在`本次任务/`中自行形成本人任务卡并放入当前新需求材料。
- 系统基线可以保留通用布局、组件和交互规范，但应移除固定业务测试题。
- 负责人不预先指定或填写参测需求；产品经理不得复制其他人的个人任务卡、个人目录或反馈表作为自己的输入。
- 新需求是否与历史案例相似不影响隔离要求；Codex必须从当前资料重新建立事实和契约。
- `workflow/`内的空白任务卡、总结和反馈表均为`TEMPLATE_ONLY`。根目录待填写任务卡在完成本人信息并重命名为`个人任务卡_姓名_需求名称.md`后，才可作为本次任务事实来源。
- 若启动时尚无合格任务卡，Codex只收集姓名、需求名称、业务原话或资料路径三项最小信息并代为生成任务卡；不得让负责人替产品经理决定测试内容，也不得先让产品经理填写完整问卷。
- 工作流规则路径必须相对解压根目录中的`workflow/`，当前需求路径必须相对`本次任务/`，不依赖负责人电脑、产品经理电脑或历史项目的绝对路径。
- 包内必需目录缺失时判定发包不完整并请求补包，不允许跨电脑猜测兜底路径。
