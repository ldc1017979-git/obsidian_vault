# 端口分流与资料引导卡

本文件用于 Codex 启动项目时快速分流。它不是产品经理开局要填写的问卷，而是 Codex 背后的引导卡。

## 0. 三轮之前先做阶段0

先按20号规范检查旧案例隔离、个人任务卡与原始资料冲突，并确定项目终点。产品经理本人、项目名、真实问题、承载系统、跨系统/库存/台账边界存在未关闭冲突时，不开始三轮漏斗中的正式产品判断；业务或研发负责人暂不清楚时先登记待确认。

## 1. 启动三轮漏斗

Codex 启动任何产品项目时，必须按三轮推进：

| 轮次 | 只确认什么 | 不要提前问什么 |
|---|---|---|
| 第一轮 | 端口/业务域：工厂端、供应链、市场端、跨域协同、不确定 | 不要追问完整字段、权限、页面和接口 |
| 第二轮 | 是否有知识库、现有系统资料、历史资料、截图、录屏、旧 PRD、字段表、规范文档、设计规范来源 | 不要在未读资料前重复问资料里已有内容 |
| 第三轮 | 需求变化类型、系统承载关系、是否继承现有系统基线、设计规范采用哪种来源 | 不要默认套用数智工厂或任何单一系统风格 |

三轮中客观事实从资料抽取，不做选择题；局部优化每阶段默认3-6个关键决策，超过预算必须解释资料缺口或冲突来源。

如果产品经理第一句话已经提供了足够信息，Codex 可以一次性输出初步判断，但必须仍然覆盖这三轮的结论和依据。

## 2. 第一轮端口选项

第一轮固定使用下面选项，允许产品经理组合或选择“不确定”。

| 选项 | 端口 | 判断线索 | 后续重点 |
|---|---|---|---|
| A | 工厂端 | 生产、质量、设备、安全、仓储现场、工厂运营 | 工单、工序、设备、质检、异常、班次、现场效率 |
| B | 供应链 | 采购、供应商、订单、库存、物流、履约、计划协同 | 上下游对象、单据流、库存规则、交付规则、协同边界 |
| C | 市场端 | 门店、渠道、客户、会员、活动、积分、销售、终端运营 | 用户触点、活动规则、权益规则、渠道数据、运营指标 |
| D | 跨域协同 | 多端口、多系统、多角色共同完成一个流程 | 主端口、承载系统、数据流、责任边界、异常回传 |
| E | 不确定 | 产品经理只有想法，暂时无法归类 | Codex 先给建议判断，再让产品经理确认 |

第一轮回复必须包含：

- 当前初判。
- 判断依据。
- 推荐选择。
- 推荐理由。
- 选错会影响什么。
- 请产品经理确认或纠正。

## 3. 第二轮资料来源选项

端口确认后，第二轮只问资料来源。

```text
你现在有下面哪些资料？可以多选，没有也没关系。

A. 知识库或历史资料目录
B. 现有系统链接或测试环境
C. 典型页面截图或操作录屏
D. 旧 PRD、流程图、会议纪要
E. 字段表、Excel、纸质单据或接口字段
F. 已集成在本工作流里的系统规范或基线
G. 产品提供的设计规范文档，比如 Figma、Axure、蓝湖、组件库、UI 规范、交互规范
H. 暂时都没有
```

处理规则：

- 有 A/B/C/D/E/G：先读取、抽取、归纳，再追问缺口。
- 有 F：先读取已集成规范，输出基线引用说明。
- 只有一句话需求：继续用选择题引导，不要求产品经理补完整 PRD。
- 资料有冲突：列出冲突点，让产品经理确认，不自行拍板。
- 资料缺失但不阻塞：标记“暂不影响”，继续推进下一轮。
- 资料缺失且阻塞：只要最小补充项，不开长问卷。

### 3.1 设计规范来源必须单独判断

设计规范来源分四类，不能混在一起：

| 类型 | 来源 | Codex 动作 | 是否需要产品确认 |
|---|---|---|---|
| A. 已集成规范 | 工作流中已经沉淀的系统风格基线、菜单结构、组件规则、交互规则 | 直接读取对应规范，输出“基线引用说明” | 需要确认是否适用于本项目 |
| B. 链接反推规范 | 产品提供现有系统链接、测试环境、截图、录屏、同类页面 | Codex 先提取页面结构、组件、交互和视觉规律，再输出“反推设计规范摘要” | 必须产品确认后才能作为项目基线 |
| C. 产品提供规范文档 | Figma、Axure、蓝湖、组件库、UI 规范、交互规范 | Codex 按 10 完整性清单先提炼规范摘要、组件规则、页面规则和冲突点 | 必须产品确认后才能作为项目基线 |
| D. 暂无规范来源 | 没有已集成规范、现有系统资料或产品规范文档 | 只能输出业务结构稿或页面结构草稿 | 不允许生成最终风格 HTML |

处理规则：

- 如果承载系统已有“已集成规范”，优先读取该规范，不要求产品经理重复描述。
- 如果产品同时提供现有系统链接、截图或规范文档，Codex 必须对比“已集成规范”“当前系统页面”“产品规范文档”，列出一致点、差异点、疑似版本变化和冲突项，让产品确认采用哪一个。
- 如果没有已集成规范，但有现有系统链接或截图，Codex 必须先反推规范，再给产品确认，不能直接生成最终 UI。
- 如果有产品规范文档，Codex 必须先提炼为项目基线，再给产品确认，不能只把文档当素材参考。
- 使用产品规范文档时，必须执行 `10-产品提供规范文档提炼完整性清单.md`。
- 如果没有任何规范来源，只能输出业务结构稿或页面结构草稿，不能声称已完成最终风格 HTML。

## 4. 第三轮承载和基线判断

第三轮才判断：

| 维度 | 选项 | 影响 |
|---|---|---|
| 需求变化类型 | 旧功能优化 / 现有系统新增模块 / 数据看板 / 集成改造 / 不确定 | 决定先读旧功能、补新模块、定指标口径还是拆系统边界 |
| 系统承载关系 | 现有系统内建设 / 完全独立新系统 / 跨系统 / 不确定 | 决定是否继承菜单、页面壳、组件、交互、权限和 UI |
| 系统基线 | 数智工厂 / 供应链系统 / 市场系统 / 其他系统 / 独立新设计 / 待确认 | 决定 HTML 原型视觉和交互依据 |
| 设计规范来源 | 已集成规范 / 链接反推规范 / 产品提供规范文档 / 暂无 | 决定 Codex 是直接读取基线、先反推规范、提炼规范文档，还是只输出结构稿 |

重要规则：

- 业务功能是新的，不等于系统可以从零设计。
- 承载在现有系统内，就必须继承该系统的菜单、页面壳、组件、交互、权限和 UI 风格。
- 承载在供应链或市场端已有系统内，必须读取对应系统资料，不能套数智工厂基线。
- 承载系统不确定时，不能生成最终 UI 风格原型，只能输出业务结构稿或待补资料清单。

## 5. 各端口后续引导重点

### 5.1 工厂端

优先确认：

- 工厂业务对象：工单、设备、物料、质检、异常、班次、仓储、人员。
- 主流程：发起、执行、确认、异常、关闭。
- 状态：草稿、待处理、处理中、待确认、已完成、已作废等。
- 现场效率：少录入、可追溯、异常闭环、移动端或大屏是否需要。

现有系统资料优先级：

1. 数智工厂系统基线或工厂端现有系统截图。
2. 旧页面、菜单、权限、同类模块。
3. 现场单据、Excel、纸质记录、设备数据。

### 5.2 供应链

优先确认：

- 上下游对象：采购方、供应商、仓库、物流、计划、财务。
- 单据流：订单、采购单、送货单、入库单、对账单、退货单。
- 协同规则：谁发起、谁确认、谁修改、谁审批、谁可见。
- 履约和库存：交期、缺货、部分到货、超收、退货、冻结、预警。

现有系统资料优先级：

1. 供应链系统链接、菜单、列表页、详情页、表单页、审批页。
2. 供应商端或内部端角色权限说明。
3. 订单、库存、物流、对账等字段表或历史 PRD。

禁止：

- 在没有供应链系统资料时，直接套数智工厂页面壳作为最终 UI。
- 把采购测试案例字段迁移到非采购模块。

### 5.3 市场端

优先确认：

- 业务对象：门店、渠道、客户、会员、活动、权益、积分、销售、终端人员。
- 用户触点：后台配置、门店执行、客户参与、核销、反馈、统计。
- 活动和权益规则：参与条件、发放、使用、过期、撤回、异常处理。
- 数据指标：参与数、转化、核销、销售、活跃、排行、渠道对比。

现有系统资料优先级：

1. 市场系统、门店系统、会员系统或运营后台链接/截图/录屏。
2. 活动配置、积分规则、权益规则、核销流程。
3. 门店、渠道、用户、订单或销售数据字段。

禁止：

- 把市场端做成工厂端现场流程。
- 在没有市场端系统资料时，直接套数智工厂页面壳作为最终 UI。
- 只做营销展示页，忽略后台配置、执行、核销和统计闭环。

### 5.4 跨域协同

优先确认：

- 主端口：最终谁主责，页面主要给谁用。
- 承载系统：页面最终落在哪个系统。
- 数据流：从哪个系统来，到哪个系统去，谁写入，谁只读。
- 责任边界：谁发起、谁审批、谁执行、谁确认、谁处理异常。
- 异常回传：失败、驳回、超时、撤回、重复、权限不足如何处理。

现有系统资料优先级：

1. 所有相关系统的入口、角色、页面和接口/字段线索。
2. 当前线下流程或跨部门协作记录。
3. 历史会议纪要、冲突点、未定责任边界。

禁止：

- 未确认承载系统就进入最终 UI 原型。
- 只画一个系统页面，忽略其他系统的数据和责任边界。

## 6. 输出格式要求

每轮结束必须输出：

```text
本轮已确认：
暂定假设：
待业务确认：
待研发确认：
你刚刚完成的产品判断：
这个判断会影响：
下一步：
```

不得把 Codex 推荐项写成已确认业务事实。
