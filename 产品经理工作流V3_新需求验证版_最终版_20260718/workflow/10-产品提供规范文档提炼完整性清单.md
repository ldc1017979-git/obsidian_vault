# 产品提供规范文档提炼完整性清单

本文件用于 Codex 在产品经理提供 Figma、Axure、蓝湖、组件库、UI 规范、交互规范或设计稿截图时，把资料提炼成可执行的项目设计基线。目标不是简单“参考设计稿”，而是让后续 HTML 原型能稳定继承对应系统的页面层级、组件规则、交互方式和视觉风格。

如果产品提供规范文档，Codex 必须先执行本清单，输出“规范文档提炼摘要”，经产品经理确认后才能作为最终视觉基准。

## 2. 最少提炼范围

只要规范文档用于生成最终风格 HTML，至少要覆盖下面内容。没有覆盖的部分必须标记“未体现/待确认”，不能自行补成确定规则。

| 范围 | 必须提炼什么 |
|---|---|
| 系统壳 | 顶部导航、侧边菜单、页签、面包屑、全局工具区、登录态用户区 |
| 页面层级 | 一级入口、二级页面、隐藏新增页、编辑页、详情页、弹窗、抽屉、返回路径 |
| 页面类型 | 列表页、表单页、详情页、配置页、报表页、看板页、审批页或移动端页面 |
| 组件规则 | 按钮、输入框、选择器、日期、上传、表格、分页、Tabs、状态标签、Dialog、Drawer、Toast |
| 视觉规则 | 主色、辅助色、状态色、背景、内容容器、字体、字号、间距、圆角、线条、阴影、图标 |
| 布局密度 | 后台工具型密度、表格行高、筛选区高度、表单列数、页面留白、内容最大宽度 |
| 交互规则 | 新增、编辑、详情、删除、提交、审批、撤回、导出、批量操作、二次确认、异常反馈 |
| 权限规则 | 菜单权限、按钮权限、数据范围、字段可见/可编辑、无权限态 |
| 状态规则 | 草稿、待处理、已提交、已审批、已驳回、已作废等状态及可操作按钮 |
| 空态和异常 | 无数据、加载、失败、校验错误、接口异常、部分成功、无权限 |

## 3. 证据分级

提炼结果必须区分证据来源，不能把推断写成确定规则。

| 证据级别 | 含义 | 可否作为最终规则 |
|---|---|---|
| 文档明确规定 | 规范文档或组件库明确写出 | 可以，但仍需产品确认适用范围 |
| 设计稿明确可见 | 页面截图或设计稿中能直接看到 | 可以，但要说明来自哪个页面 |
| Codex 基于样例推断 | 多个页面呈现一致规律，但文档未写明 | 需要产品确认 |
| 与现有系统冲突 | 规范文档和当前系统页面不一致 | 不能自行拍板，必须产品确认 |
| 未体现 | 资料里没有出现 | 不能当成最终规则 |

## 6. HTML 适配规则

如果规范文档来自 Figma、Axure 或蓝湖，Codex 不能只做静态截图复刻。必须转成可交互的 HTML 原型规则：

- 页面结构要按真实业务入口和返回路径组织。
- 表格、筛选、表单、详情、弹窗、抽屉必须可操作。
- 按钮必须产生真实状态变化或反馈。
- 状态标签、权限显隐、二次确认要和业务规则联动。
- 设计稿只覆盖单页时，不能推导成全系统完整规范。
- 如果规范是移动端、H5 或 App，不能直接套到后台管理系统，必须确认承载端。

## 7. 一票否决项

出现以下情况，不能生成最终风格 HTML：

- 未说明规范文档来源、版本和适用范围。
- 只提炼颜色、字体，没有提炼系统壳、页面层级、组件和交互。
- 把单个页面设计稿当成全系统规范。
- 文档与现有系统页面冲突，但未让产品经理确认采用哪个。
- 没有区分“文档明确规定”“设计稿可见”“Codex 推断”“未体现”。
- 未输出“规范文档提炼摘要”就直接生成最终风格 HTML。
- 保存账号、密码、token 或真实登录链接。
